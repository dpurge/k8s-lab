## Problem / Motivation

In production (jdpct101, image 2026.10.0), generating vocabulary for an Arabic
text (Nizar Qabbani) produced an empty list: job `generate_vocab_from_text`
finished `done` with result `{"list_id": 10, "item_count": 0}` after 794s,
while other texts (e.g. "The Brave Hunter") work.

Root cause, reproduced in dev (k3d) with the same prompt, model
(`gemma4:12b`, `numCtx` 8192) and a 3618-char Arabic text: the model returned
89 well-formed lines in the shape `phrase [noun] [translit] = meaning`
(grammar in square brackets) instead of the prompted
`phrase {grammar} [transcription] = translation`.
`generate.ParseVocabularyLines` silently skips any line that does not match
its regex, so all 89 lines were dropped (`items=0` in a replay against the real
parser). `HandleGenerateVocab` and `HandleGenerateModels` then save the empty
list and report success, so the failure is invisible. Format adherence varies
by language/text, which is why other texts work.

Related weaknesses found in the same code path:

- `HandleGenerateVocab`/`HandleGenerateModels` call `ai.Generate` (one call),
  not `GenerateChunked`; long texts can exceed `numCtx` and Ollama truncates
  silently.
- `ai.chunkRunes` assumes 3 chars/token with half the window for input. The
  Arabic sample measured about 1.6 chars/token (3618 chars -> 2238 tokens;
  1653 reply tokens). A full 10752-char chunk would need roughly 11k tokens in
  total against 8192 (estimate from one sample, to be verified).
- The models parser (`modelsLinePattern`) has the same strict shape and the
  same silent-skip behaviour; not yet replayed with a real models generation.

Assumptions: the prod slowness (794s vs about 3 min in dev) is CPU vs GPU
(confirmed by the user). An already-empty prod list is regenerated by the user
after deployment; no prod data is changed by this work.

## Acceptance Criteria

- [ ] Parsing stays strict: vocabulary lines must be `phrase {grammar} [transcription] = translation` (grammar, transcription and translation each optional; grammar only in `{}`, transcription only in `[]`); models lines must be `phrase [transcription] = translation`.
- [ ] `ParseVocabularyLines` and `ParseModelsLines` return the valid items and the rejected non-blank lines, each with a specific error reason; blank lines are ignored.
- [ ] Rejected lines (only those, with their errors; never the already-valid lines and never the source text) are sent back to the model in a small correction call that states the required format; corrected lines are re-parsed and any still rejected are sent again, up to the purpose's `MaxAttempts` rounds (transient LLM errors keep using the existing retry path).
- [ ] After the correction rounds, lines still rejected are dropped; the valid items are saved and the job result records `skipped_lines: N`. If zero valid items remain while the model returned non-blank output, the job fails with an error that includes the first rejected lines (truncated). Applies to both vocabulary and models.
- [ ] Vocabulary and models generation split long text into chunks sized so input plus expected output fits `numCtx` for dense scripts (diacritized Arabic included); each chunk's reply goes through the same parse-and-correct step; items are de-duplicated across chunks, keeping first-occurrence order.
- [ ] Tests (no network, injected LLM): strict parser accepts the documented format and rejects the captured Arabic `[tag] [translit]` lines with a reason; correction round resends only rejected lines; drop-and-count and fail-on-zero behaviour; chunked generation with cross-chunk de-duplication.
- [ ] In dev, replaying the Arabic text through the real job queue yields a non-empty vocabulary list; `cd phraseforge && go test ./...` passes.

## Approach

Ordered, each step shippable and reviewed before the next:

1. **Strict parser with per-line errors** (`internal/generate/parse.go`):
   keep the current regexes; change the Parse*Lines API to return items plus
   rejected lines with reasons. Tests include the captured Arabic output.
2. **Line-level correction** (new small unit in `internal/ai`): given rejected
   lines and their errors, call the model with a short system prompt (required
   format, "return only corrected lines in the same order, one per line") and
   a user message listing the lines and errors. Spike result (dev, `gemma4:12b`):
   12 of 12 lines corrected in about 22s from a 373-token prompt, all accepted
   by the real parser. Reuse `effectiveMaxAttempts` and `callLLM`; do not reuse
   `runWithCorrection`, which resends the whole reply with a JSON-only message.
   Wire into `HandleGenerateVocab`/`HandleGenerateModels` with drop-and-count
   and fail-on-zero (the existing "partial beats failed" comment on
   `ParseVocabularyLine` stays true for some-valid; zero-valid becomes an error).
3. **Chunking**: handlers call a chunked path; recalibrate the chunk size for
   dense scripts (default: conservative 1.5 chars/token, input plus reply
   within `numCtx`); de-duplicate items across chunks. Existing chunking for
   ingest (`GenerateChunked`) must keep its behaviour or have its tests updated
   deliberately.
4. **Verify in dev**: replay the Arabic text via the job queue; confirm
   `item_count > 0` and `skipped_lines`.

Alternatives considered: accept `[tag] [translit]` in the parser (rejected by
the user: parser stays strict); change the prompt to ask for `[...]` only
(would alter behaviour for languages that work today); resend the whole reply
for correction (rejected by the user: only unparsable lines go back).

Risks: the model may not fix some lines (handled by drop-and-count); more LLM
calls on a CPU-only node (correction calls are small); chunk-size change
affects ingest if the shared function is changed.

## Affected Areas

- `phraseforge/internal/generate/parse.go`, `generate.go` and their tests
- `phraseforge/internal/ai/` (new correction unit, `chunk.go` sizing, tests)
- `phraseforge/CHANGELOG.md` (user-facing fix entry)

## Out of Scope

- Changing the prompts, the parser's accepted format, or the default model.
- Repairing the existing empty prod list or any prod data (regenerated by the user after deployment).
- Item-translation jobs (`generate_vocabulary_item`), which already have their own JSON correction path.
- Backfilling `translation` from `= translation` (unchanged, per the earlier export/import spec).

## Implementation Notes

Working on `main`, nothing committed (the user commits).

- **Step 1 (done): strict parser with per-line errors.** `internal/generate/parse.go`: `ParseVocabularyLines`/`ParseModelsLines` now return `(items, []RejectedLine)`; blank lines ignored; reasons name grammar-in-brackets, a second `[...]` group, a missing phrase, or a generic format mismatch. Regexes unchanged. Tests use lines captured from the dev replay.
- **Step 2 (done): line-level correction.** New `internal/ai/correctlines.go` (`CorrectLines`, `CorrectionRounds`, `correctionMessages`): a small call with only the rejected lines and their errors, via `callWithRetry` so transient errors keep the existing retry path and the loaded model/`numCtx` is reused. New `internal/generate/correct.go`: generic `parseWithCorrection` (rounds = purpose `MaxAttempts`; corrected items follow the valid ones; lines still bad are dropped and counted; a failed correction call keeps the valid items; zero valid items from non-blank output is an error quoting the first rejected lines). Both handlers use it; job result gains `skipped_lines` (omitted when 0). Tests: `correct_test.go` (loop), `correctlines_test.go` (messages and fake-Ollama request shape). Not yet exercised against a real model through the job queue (step 4).
- **Step 3 (done): chunked generation.** `internal/ai/chunk.go`: new `Service.ChunksFor(kind, content)` and a dense sizing of 1.5 runes/token (8192 ctx -> 5376 runes per chunk; the 3618-rune Arabic sample stays one chunk). Superseded by `phraseforge-ingest-very-long-texts` step 2, which applies the same single `chunkRunes` to every kind including ingest. `internal/generate/correct.go`: `parseWithCorrection` now returns the still-rejected lines instead of failing; new generic `generateItems` runs chunk by chunk, parses and corrects each reply, drops items an earlier chunk already produced (repeats within one chunk are kept), skips a chunk with nothing valid, and fails only if no chunk yielded a valid item although the model answered (blank content stays an error as before). Handlers call it. Tests added for the aggregator and the sizing.
- **Known gap at the time, since addressed:** ingest sized chunks at 3 runes/token; see `phraseforge-ingest-very-long-texts`.
- **Step 4 (done): dev replay through the job queue.** Deployed with `task deploy-phraseforge` and queued `generate_vocab_from_text` for the dev Arabic text (3617 chars, one chunk). Run 1: `{"list_id": 12, "item_count": 101}`. After adding a per-round log line (`corrected rejected lines`, counts only) and redeploying, run 2 logged `round=1 sent=81 recovered=81 still_rejected=0` and finished `{"list_id": 12, "item_count": 81}`: the first model reply had no valid line (the production failure) and one correction round recovered all of them. The item count differs between runs because the model is not deterministic.
- Also added: `slog` info line per correction round (counts only, no model output).

## Validation

- `cd phraseforge && go build ./... && go vet ./... && gofmt -l .`: clean.
- `cd phraseforge && go test ./...`: all packages pass (baseline before changes also passed, so no regression). New tests: `internal/generate/parse_test.go`, `correct_test.go`, `internal/ai/correctlines_test.go`, `chunk_test.go`.
- Dev replay (see Implementation Notes step 4): the production failure (zero valid lines from the first reply) reproduced on the real model and was recovered by one correction round; job result `item_count > 0`, no `skipped_lines`.
- Later observation in dev (user-submitted jobs, 2026-10-05 14:24 UTC, after the ingest follow-up steps 1-5 were deployed): vocabulary and models generation for the Arabic text "The Brave Hunter" (text 23) finished with 74 and 19 items, no correction round was needed (the model used the `{grammar}` format on the first call), and token use was healthy (vocabulary 1316 prompt + 1416 reply, models 1295 + 557, against `num_ctx` 8192). This is the first real-model run of models generation, and it also shows that two Arabic texts, same model and prompt, differ in format adherence, which is why only some texts failed in prod.
- Coverage gaps: models generation was exercised on the real model only through that one run (no malformed output happened to occur, so the models correction round itself is unit-tested only); chunking was exercised by unit tests only, since the dev text fits one chunk; the handlers themselves have no DB-backed test.
- `reviewer` not invoked: not security-sensitive; architecture limited to the generate/ai packages.
