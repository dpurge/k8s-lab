## Problem / Motivation

Today, creating a Text or Dialog in phraseforge requires filling in Title, Body, Language, Script, Transcription, and Translation all up front through the "New" form. This feature adds an "Ingest" path: paste text/markdown, upload a local `.md`/`.txt` file, or fetch a URL — only Body (raw content), Language, and Script are required at ingest time. Title, a cleaned-up Body, Transcription, and Translation are generated by background jobs, building on the job queue (`phraseforge-job-queue`, done) and its admin Jobs page (`phraseforge-jobs-menu`, done).

This feature fills a gap flagged when `phraseforge-shared-model-config` was built: that feature's config/prompt system supports only two purposes (`transcription`, `translation`), deliberately deferring `generate_title` and other future purposes to whichever feature actually needs them. This feature adds three new LLM purposes: `title` (generates a short title from body content), `process_text` (cleans raw ingested content into markdown prose suitable as a reading text — strips navigation/ads/boilerplate from URL-sourced HTML, lightly normalizes pasted/file content), and `process_dialog` (produces dialog-turn-structured content instead of prose). `process_text` and `process_dialog` are deliberately separate purposes/kinds, not one shared kind, because `llm_prompts` is keyed by `kind`, not by resource type — a single shared "process" kind could not have independently-tunable default prompts for texts (prose) versus dialogs (turn-structured), and the user explicitly wants each purpose independently configurable per language, with more purposes expected to follow this same one-kind-per-purpose pattern in future features.

The ingest pipeline is asynchronous: raw content is resolved synchronously (fetched from URL, read from uploaded file, or taken as pasted text), then staged in a background job's payload. A `process_text`/`process_dialog` job cleans the content and generates the title, creates the actual Text/Dialog row, and enqueues follow-up jobs (one `generate_translation` per site locale, and one `generate_transcription` if the language needs it). Authorization reuses the existing "New" button's `CanEdit` check — ingest is not admin-gated.

## Acceptance Criteria

- Three new LLM purposes added to `phraseforge/internal/config`'s provider-registry config shape (`title`, `process_text`, `process_dialog`), each with fields `{provider, model, numCtx, think}`, defaulting to `ollama`/`gemma4:12b`/`think: false`; `process_text`/`process_dialog`/`title` default `numCtx: 8192`, while `transcription`/`translation` keep their existing (unset/0) default.
- `llm_prompts`' `kind` CHECK constraint expands from `('translation','transcription')` to also allow `'title'`, `'process_text'`, `'process_dialog'`, each independently admin-overridable per (kind, source_language, target_language) via the existing admin LLM-prompt UI.
- `ai.Service.Generate` supports all five kinds via a proper per-kind lookup (replacing the current two-way "transcription vs. everything-else-is-translation" branch), each with its own built-in default prompt: `title` writes a short, specific title and responds with only the title text; `process_text` reformats raw extracted text into clean Markdown prose, stripping navigation/ads/boilerplate, preserving paragraph structure, no translation/summarization; `process_dialog` reformats raw extracted text into a clean dialog transcript, one turn per line, stripping navigation/boilerplate.
- `texts` and `dialogs` tables each gain a nullable `ingest_source text` column (additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) recording the URL or original filename a row was ingested from; `NULL` for manually-created or pasted-text-ingested rows.
- New job kinds `process_text` and `process_dialog` (new dedicated handlers in new package `phraseforge/internal/ingest`), reusing the existing `llm_generate` kind for `generate_translation`/`generate_transcription` with extended payload.
- `llm_generate`'s payload gains optional `resource_type` (`"text"`|`"dialog"`), `resource_id`, and `locale` (translation only) fields; when `resource_id` is non-zero, `HandleGenerate` writes the result back instead of only returning it to an awaiting caller.
- New narrow setter methods `texts.Store.SetTitle`/`SetTranscription` and `dialogs.Store.SetTitle`/`SetTranscription` (single-column `UPDATE ... SET x=$1, updated_at=now() WHERE id=$2`) so a background job's completion never clobbers a field it didn't touch, even if jobs complete out of order.
- New `POST /api/v1/texts/ingest` and `POST /api/v1/dialogs/ingest` endpoints: request `{source: "url"|"file"|"text", url?, filename?, content?, language, script}` (`content` required for `"file"`/`"text"` — already read client-side for a file upload via `FileReader`; `url` required for `"url"`, fetched server-side with a timeout and response-size cap, HTML content-type responses stripped to plain text). Response: `{"job_id": "<uuid>"}`. Authorization: `CanEdit(language)`, not admin-gated. Raw content capped at 200 KB, rejected with 400 if exceeded.
- New "Ingest" button next to "New" on the Texts and Dialogs list views, opening a form: source selector (URL / paste text / upload file), the matching conditional field, Language/Script selects (reusing the existing New-form selects). On submit, shows an acknowledgment (e.g. "Ingestion started") and returns to the list — no live progress for a non-admin user.
- `go build ./...`, `go vet ./...`, `go test ./...` pass. A real end-to-end pass exercises the smallest practical content (a one-or-two-sentence body) for exactly one ingest path (e.g. paste-text for a Text, in a language that needs transcription, to exercise every job kind at least once) rather than exhaustively testing every source type × resource type combination live; URL-fetch and file-content handling are validated statically/structurally wherever a live LLM call is not required.

## Approach

1. **`phraseforge/internal/config/config.go`**: add `Title`, `ProcessText`, `ProcessDialog` fields (each `PurposeConfig`) to `Config`/`fileConfig`, with the defaults described in Acceptance Criteria.
2. **`phraseforge/internal/db/schema.sql`**: expand `llm_prompts`'s `kind` CHECK constraint to include `'title'`, `'process_text'`, `'process_dialog'`. Add `ingest_source text` (nullable, additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) to both `texts` and `dialogs`.
3. **`phraseforge/internal/ai/ai.go`**: replace the current two-way `purposeDefault`/prompt-kind branch with a proper switch/map over all five kinds; add each new kind's built-in default prompt text.
4. **`phraseforge/internal/texts/texts.go`, `phraseforge/internal/dialogs/dialogs.go`**: add `SetTitle(ctx, id, title) error` and `SetTranscription(ctx, id, transcription) error` narrow setters; add `ingest_source` to `Create`'s parameters (nullable) and to the struct/select columns.
5. **`phraseforge/internal/ai/ai.go` (HandleGenerate)**: extend the payload type with optional `ResourceType`/`ResourceID`/`Locale` fields; after a successful `Generate` call, if `ResourceID != 0`, dispatch the writeback via a small consumer-side interface (satisfied by `texts.Store`/`dialogs.Store` and `translations.Service`) instead of (or in addition to) returning the result.
6. **New `phraseforge/internal/ingest` package**: `HandleProcessText`/`HandleProcessDialog` — unmarshal the raw payload (content, source, language, script, user id, resource type), call `ai.Service.Generate(ctx, "process_text"|"process_dialog", ...)`, then `ai.Service.Generate(ctx, "title", ...)` directly, create the row with the new `ingest_source` parameter, then enqueue: one `llm_generate` job per site locale with `kind="translation"` and the resource fields set; and, if the language needs transcription (reuse the existing ime-config check), one more `llm_generate` job with `kind="transcription"` and the resource fields set.
7. **`phraseforge/internal/server`**: new `apiIngestText`/`apiIngestDialog` handlers implementing the endpoint contract (URL fetch with timeout/size cap and HTML-to-text stripping — adapt knowledge's existing `stripHTML` approach — content-size cap, `CanEdit` check, enqueue the `process_text`/`process_dialog` job, return the job id). Register the two routes alongside the existing `/api/v1/texts`/`/api/v1/dialogs` routes.
8. **`phraseforge/main.go`**: register the two new job kinds (`process_text`, `process_dialog`) against the `ingest` package's handlers.
9. **Frontend**: `texts-app.js`/`dialogs-app.js` gain an "Ingest" button next to "New", opening a small form (source selector + conditional field + Language/Script selects, reusing existing selects/components) that calls the new endpoint and shows an acknowledgment.
10. **i18n**: add new labels for the Ingest form/button (en + pl), following established per-file/section i18n key conventions.

## Out of Scope

- Vocabulary/Models generation triggered automatically on ingest — that is `phraseforge-generate-vocab-models-from-text`'s scope.
- Sophisticated content cleanup beyond a reasonable default prompt — deeper navigation-stripping heuristics and learner-level-aware simplification are future enhancements to the `process_text`/`process_dialog` purposes' prompts, not new kinds.
- A live-progress indicator for non-admin ingesting users — the Jobs page stays admin-only per `phraseforge-jobs-menu`'s existing decision.
- Export/Import (YAML) — `phraseforge-export-import`'s own scope.
- A `TitleDirect`-style bypass mechanism as a general pattern — not needed here and not built preemptively for hypothetical future need.
- Retry/cancel semantics specific to a failed ingest pipeline step — failed jobs are handled by the existing generic Jobs page.

## Implementation Notes

All 10 Approach steps implemented across 4 sequential passes, each verified to build/vet/test clean before the next started. Full repo (`shared`, `phraseforge`, `knowledge`) builds clean after all 4.

**Pass 1 (steps 1-5, backend core):**
- `phraseforge/internal/config/config.go`: added `Title`/`ProcessText`/`ProcessDialog` `PurposeConfig` fields, defaulting to `ollama`/`gemma4:12b`/`numCtx:8192`/`think:false` (the 8192 differs deliberately from `Transcription`/`Translation`'s unset default, per the spec).
- `phraseforge/internal/db/schema.sql`: `llm_prompts_kind_check` dropped/recreated to allow `title`/`process_text`/`process_dialog`; `ingest_source text` (nullable) added to `texts`/`dialogs`. Verified idempotent and correctly upgrading an existing installation via a live throwaway-Postgres test during implementation (not just by inspection).
- `phraseforge/internal/ai/ai.go`: `purposeDefault`/prompt-lookup now a proper 5-way switch (was a 2-way branch), with built-in default prompts for the three new kinds. `HandleGenerate`'s payload gained optional `ResourceType`/`ResourceID`/`Locale`; when `ResourceID != 0` it writes the result back (`TextWriteback`/`TranslationWriteback` — small consumer-side interfaces satisfied by `texts.Store`/`dialogs.Store`/`translations.Service`) instead of only returning it — the existing interactive path (`ResourceID == 0`) is unchanged. `ai.New(...)`'s signature grew accordingly; `main.go`'s one call site was updated.
- `texts.go`/`dialogs.go`: new narrow `SetTitle`/`SetTranscription` setters (avoid clobbering fields from out-of-order background completions); `Create` gained an `ingestSource` parameter (existing call sites pass `""`).

**Pass 2 (step 6 + half of step 8, ingest job handlers):**
- New `phraseforge/internal/ingest` package: `HandleProcessText`/`HandleProcessDialog` (kinds `process_text`/`process_dialog`) — clean the raw content via `ai.Generate`, generate the title via a direct (non-enqueued) `ai.Generate` call, create the row (recording `ingest_source`), then enqueue follow-up `llm_generate` jobs: one `generate_translation` per site locale (`en`, `pl`) and one `generate_transcription` if the language needs it (existing ime-config check). Both `ai.Generate` calls inside the handler are plain synchronous calls — confirmed no deadlock risk, since `ai.Service.Generate` was never queue-aware itself in this architecture (unlike knowledge's equivalent), so no `TitleDirect`-style bypass method was needed.
- Verified against real code (not assumed) that transcription's `target_language` must be the sentinel string `"transcription"`, not the real language — matching the existing interactive `/llm/generate` convention exactly, since `llm_prompts` overrides are looked up by the literal `(kind, source_language, target_language)` triple and getting this wrong would silently bypass any admin-configured transcription prompt.
- Confirmed manually-created dialogs are never `{start-dialog}`-wrapped before `Create` (wrapping happens at render time only) — ingested dialogs are stored the same way, for consistency.
- `main.go`: registered `ingest.KindProcessText`/`KindProcessDialog` against the new handlers, alongside the existing `llm_generate` registration.

**Pass 3 (step 7 + rest of step 8, HTTP endpoints):**
- New `POST /api/v1/texts/ingest`/`POST /api/v1/dialogs/ingest` (inside the existing `requireAuth` group, `CanEdit(language)`-gated, same as the existing create endpoints — not admin-gated). Request: `{source, url?, filename?, content?, language, script}`. Response: `202 Accepted` with `{"job_id": "<id>"}` (202 chosen deliberately over 201, since nothing is created synchronously — the row doesn't exist until the background job runs).
- URL fetch: 15s timeout, 5 MB response cap (oversized responses are rejected with 400 rather than silently truncated, since a truncated HTML document could leave content that survives `stripHTML` with garbage in it); HTML responses stripped to plain text (ported from knowledge's `stripHTML`, preserving its RE2-no-backreferences handling of multiple closing-tag alternatives). Final content capped at 200 KB (checked after any stripping) with a 400 if exceeded.
- No new `Server` constructor parameters were needed — `jobs *jobs.Service` was already available from the earlier job-queue/jobs-menu features.

**Pass 4 (steps 9-10, frontend + i18n):**
- New "Ingest" button next to "New" on both Texts and Dialogs list views (same `canCreateAny` gating as New). Clicking it swaps the section into an in-page ingest form (matching the existing New/Edit form pattern exactly — a floating modal was considered but ruled out, since `pf-dialog` is confirm-only, not a general form container, and inventing a new modal mechanism for this one form wasn't justified).
- Source picker (paste text / upload file / fetch URL) with conditional fields; file content is read client-side via `FileReader` (no server-side multipart); Language/Script reuse the exact same selects the New form already uses.
- New i18n keys (en + pl) added to the existing per-section `textsAppI18nKeys`/`dialogsAppI18nKeys` bootstrap lists (no parallel i18n mechanism invented): `texts.ingest`, `texts.ingest_title`/`dialogs.ingest_title`, source-option labels, field labels/placeholders, submit button, success acknowledgment, and two file-read-specific error messages.

**Known, deliberately out-of-scope gaps** (per the spec's own Out of Scope section, unchanged): no automatic vocabulary/models generation on ingest (future feature); the `process_text`/`process_dialog` default prompts are a reasonable starting point, not sophisticated navigation-stripping/learner-level-simplification (explicitly future work on the same prompts); no live-progress indicator for non-admin ingesting users (Jobs page stays admin-only); no ingest-specific retry/cancel UX (uses the existing generic Jobs page Retry). Also noting: `phraseforge/k8s/configmap.yaml` was NOT updated to explicitly enumerate the three new purpose blocks — this is not required for correctness (Go-coded defaults already match what would go in the file), but is worth a small follow-up for consistency with how `transcription`/`translation` are explicitly listed there.

**Implementation Notes addition — reviewer fix-forward round:**

A reviewer pass (this feature is large: 3 new LLM purposes, schema changes, a new writeback mechanism, a new package, new HTTP endpoints including a server-side URL fetcher, new frontend) found one blocking issue and several should-fix/security issues, all fixed:

- **Fixed (blocking)**: the three new LLM kinds (`title`/`process_text`/`process_dialog`) were rejected by the admin LLM-prompt editor's validation (`admin.go` hardcoded `translation`/`transcription` only) and absent from its UI — meaning the "admin-configurable per language" promise for these purposes didn't actually work despite the schema/config layers supporting it. Fixed by exporting a single authoritative `ai.ValidKinds`/`ai.IsValidKind` from the `ai` package and having both `admin.go` validation gates and `admin-app.js`'s kind selector read from it, so the schema, API, and UI can't drift apart again. Also fixed: the three new kinds needed a target-language sentinel convention (their own kind name, e.g. `target_language: "process_text"`) matching how `transcription` already works, since `llm_prompts` overrides are looked up by the literal (kind, source_language, target_language) triple and a real-language target was unreachable through the UI; `ingest.go` and `admin-app.js` both updated to use this convention consistently.
- **Fixed (security, user-approved)**: the URL fetch had no SSRF protection (scheme-only validation, default redirect policy, raw fetch errors echoed to the caller as a host/port-scanning oracle). Added a connect-time IP check (rejects loopback/private/link-local/unspecified/the `169.254.169.254` metadata address, checked at actual connection time so DNS rebinding and redirect targets are covered too, not just the initially-supplied URL), capped redirects to 3, and replaced the echoed raw error with a generic message (the real error is logged server-side only).
- **Fixed**: the ingest HTTP request body was unbounded before the 200KB content check ran (a large `content` field would be fully buffered into memory first) — added `http.MaxBytesReader` as the first line of the handler.
- **Fixed**: retrying a failed `process_text`/`process_dialog` job via the Jobs page could duplicate the created row (no idempotency check). Fixed using the job's `step` column (already reserved for this in the schema): the row's id is recorded there right after creation, and a retry checks for this marker before re-running the clean/title/create sequence. This required widening `jobs.HandlerFunc`'s signature to include the job's own id (a small, bounded change — only 3 registrations exist in the whole codebase) and having `jobs.Retry` carry the `step` value forward onto the new job it mints (without this, the new job would have no memory of the old one's progress, making the whole mechanism inert).
- **Fixed**: the 200KB content cap was ~6x larger than what the configured `NumCtx: 8192` context window can actually hold, meaning a large ingest would be silently truncated by Ollama with no indication. Lowered the cap to 24KB (chosen to fit comfortably within the context window, consistent with this project's goal of not overwhelming a resource-constrained machine, rather than raising the context window) and documented the relationship so a future change to one doesn't reintroduce the mismatch without the other.
- **Fixed**: language/script were only checked for non-empty presence, not validated against the actual catalog, before enqueuing — an invalid script would burn two LLM calls (process + title) before failing at the database's foreign-key constraint. Added a catalog existence check before any content resolution or enqueueing.
- **Fixed**: an LLM call that returned an empty/whitespace-only result during a background writeback would silently DELETE a previously-good translation (since `translations.Set` treats an empty body as "clear this field," by design for manual edits) instead of failing the job. Added an empty-result check that fails the job instead; also fixed writeback text to be trimmed before storage, matching the interactive path's existing behavior.
- All fixes covered by new unit tests (SSRF IP-classification, target-language sentinel conventions for the 3 new kinds, the step-column parsing logic, empty-result rejection). Full `go build`/`go vet`/`go test` clean across `phraseforge` and `shared` after this round.

**One finding, not a regression from this feature, noted for follow-up (not fixed)**: deleting a Text/Dialog does not cascade-delete its `resource_translation` rows (no FK relationship exists — `resource_type`/`resource_id` is a polymorphic pairing, not a real foreign key) — this is pre-existing behavior in `apiDeleteText`/`apiDeleteDialog`, not introduced by this feature. However, this feature is the first to make translation generation automatic/cheap (a background job on every ingest, rather than a manual click), so orphaned `resource_translation` rows will now accumulate more readily whenever an ingested item is later deleted, with nothing to clean them up. Worth a future small fix to `apiDeleteText`/`apiDeleteDialog` (delete matching `resource_translation` rows in the same transaction) — flagged for a future feature or quick fix, not blocking this one.
