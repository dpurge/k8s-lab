## Problem / Motivation

Slice B of the roadmap item `phraseforge-item-job-revisions` (slice A, the phrase rewrite, is delivered: specs/features/phraseforge-item-job-phrase-rewrite.md). A word can have several translations depending on context; the vocabulary stores them in one translation text separated by "; ". Today the item job only fills a blank translation (FillTranslation), and a known phrase (one that already has a translation or an example) gets an item job only when the step-2 check (specs/features/phraseforge-two-step-vocabulary-generation.md, delivered) marks needsExample, for the first site locale only. So when a text uses a known word in a sense the stored translation does not cover, nothing can add it. Version 2 (during step 4): the model calls showed the model does not use newSense, so the code also recovers the senses from the reply's translation; the user chose this option.

## Acceptance Criteria

- [x] The step-2 check reply per phrase becomes `{"n":1,"needsExample":true,"needsSense":false}`; CheckVocabularySchema requires n, needsExample and needsSense; the parser stays lenient (an absent or non-boolean needsSense counts as false, the outer shape rules are unchanged); the Checker interface returns, per known candidate, both verdicts; the default check prompt and its worked example ask for both, needsSense meaning the usage shows a meaning that none of the existing translations covers.
- [x] A phrase marked needsSense gets one item job per site locale in which it already has a translation (each locale needs its own sense), carrying the usage and a payload flag `sense` (an internal job field, omitted when false); a phrase marked needsExample keeps the single first-site-locale job; a phrase marked both gets one job per locale and the first-locale job serves both; locales missing a translation still get their usual jobs.
- [x] The item prompt template gains `{{translation}}`: the phrase's existing translation in the job's locale, empty when none (ItemSource carries the phrase's translations by locale); ai.PromptPlaceholders lists it for vocabulary_item; a template without it renders as before; the reply gains an optional `newSense` (string or null) in VocabularyItemSchema, decoded leniently (anything but a non-blank string means none, no correction round).
- [x] A new store call AppendSense(ctx, itemID, phrase, locale, sense) is guarded by lockItemIfStill, locks the translation row and writes `old; sense` (the old text kept as the prefix, joined with "; ") only if the locale's translation is non-blank and the sense, after trim and NFC, is not already one of the existing senses (split on ";", trimmed, compared case-insensitively); notes are untouched; otherwise applied is false without error; a sense that holds several meanings separated by ";" adds only those the translation lacks (none if nothing is new).
- [x] The job applies newSense only when its payload has `sense` true, after its other writes and before the rewrite; a skipped or failed append is logged (item id and outcome only) and the job still succeeds; the result records applied.sense; a job without the flag never appends, even if the reply carries newSense.
- [x] prompt-eval: the check prompt, schema and the cases (with expected needsSense) in check-vocabulary/; the default item prompt asks for `newSense` only when the existing translation does not cover the usage and carries the field in its worked examples; the item schema, reply validation and a few cases cover it; the item suite's reference translation var is renamed so that promptfoo does not fill `{{translation}}` with the reference answer (promptfoo fills a prompt placeholder from a test var of the same name; the rows' `translation` is the expected answer); no more than 3 real Ollama calls in total, results recorded in the spec; npm test and npm run check-sync pass (Helm-differs notes stay expected; jdp-helm not touched); the embedded defaults and the dev ConfigMap prompts (checkVocabulary, vocabularyItem) are synced and equal.
- [x] Tests without an LLM cover: the check reply parsing and the new verdicts, the job planning for needsSense, needsExample and both, the store call (prefix kept, duplicate sense not appended, blank translation not appended, stale item skipped, other list sees it), the job applying a sense only with the flag and surviving a failed append; phraseforge go build, vet and tests pass.
- [x] phraseforge/README.md and phraseforge/CHANGELOG.md describe the check's second verdict, the sense append and that deployed (Helm) prompts for checkVocabulary and the vocabulary item must be updated to get it.
- [x] When newSense is empty, a job that may append a sense recovers the new senses from the reply's translation: the senses of that translation (split on ";", compared trimmed, NFC-normalised and ignoring case) that the job's locale's existing translation lacks, joined with "; ", and only when the reply keeps every existing sense (a reply that dropped or changed one re-translated the phrase and is ignored); an explicit newSense wins; this is needed because gemma4:12b put the extra meaning into translation, not newSense, in the model calls of step 4.

## Approach

Step 1 (no model): the store call AppendSense in internal/vocabulary/itemjob.go with DB tests.

Step 2 (no model): the check pipeline: Checker returns both verdicts, ai.CheckVocabulary and the parser, the schema constant, internal/generate planning (ItemState and ItemCallLocales, NewItemJob with the sense flag), tests.

Step 3 (no model): the item job: ItemSource translations by locale, ItemPromptVars and `{{translation}}`, newSense decoding and application after the example and before the rewrite, the ItemStore interface and adapter in main.go, tests with fakes.

Step 4: prompt-eval and phraseforge prompts: check prompt and cases, item prompt, schemas (check-vocabulary, vocabulary-translation, correction/vocabulary), reply validation, the reference-translation var rename, at most 3 model calls, sync-prompts, both ConfigMap blocks, check-sync, go tests.

Step 5: docs and wrap-up.

Key decisions: the code appends, so the stored translation is never rewritten by a model: the model proposes the new sense in newSense or, as gemma4:12b did in both item calls, inside its translation, from which the code takes only the senses that are new, and only when every existing sense is kept; the flag in the payload (not the prompt alone) decides whether a job may append, so a job made for a missing locale or for needsExample alone never changes a translation; one check call per list stays (a second verdict, not a second call); a rewrite and a sense are independent and the rewrite stays last.

## Out of Scope

appending to notes or to examples differently from today; removing or editing senses; a cap on the number of senses; models items; re-translating other locales after a phrase rewrite; the jdp-helm production values; prompt tuning beyond good enough; committing anything.
