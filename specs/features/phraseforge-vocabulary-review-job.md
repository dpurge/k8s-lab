## Problem / Motivation

Roadmap item `phraseforge-vocabulary-review-job`: a vocabulary list is generated by a small local model (gemma4:12b via Ollama) and its items (phrase, grammar, transcription, per-locale translations, notes, examples) contain mistakes and padding. The user wants a Review that checks every item with a more capable model, selected in the settings by changing the provider, and shows what it would change. Decisions taken with the user: (1) the model's findings are stored as proposals and the user accepts or dismisses them in the GUI, nothing is overwritten automatically; (2) one job and one model call per item, queued by a Review button, like the item jobs; (3) a new LLM purpose `reviewVocabulary` with its own provider, model, prompt and timeout (falls back to the `vocabularyItem` model when unset); (4) a new per-language snippet, the dictionary form, rendered as `{{dictionaryPrompt}}` like the grammar and transcription snippets; a language without one skips the phrase-form check. The prompt is a first cut developed in prompt-eval and synced to phraseforge; its quality is optimised later. Text/dialog review (`phraseforge-text-dialog-review-job`) is a later item, but the purpose, job and proposal plumbing should not block it.

## Acceptance Criteria

- [ ] Languages have a third snippet, `dictionary_prompt` (column of `language_llm_sections`, added idempotently in schema.sql), editable in the admin snippets form with a default text offered next to the grammar and transcription ones; `{{dictionaryPrompt}}` is rendered in the item and review prompts (blank when the language has none).
- [ ] A default snippet file `snippet/dictionary.txt` exists in prompt-eval's prompt root and is synced into phraseforge (`npm run sync-prompts`, `check-sync` passes).
- [ ] New purpose `reviewVocabulary` (config.yaml default, Helm values, admin LLM prompts list with provider/model/think/timeout/prompt, `ValidKinds`, `purposeDefault`, `PromptPlaceholders`): when its provider/model are blank it uses the `vocabularyItem` ones.
- [ ] Review prompt `system/review-vocabulary.txt` (prompt-eval first, then synced) with placeholders `{{sourceLanguage}}`, `{{phrase}}`, `{{grammar}}`, `{{transcription}}`, `{{notes}}`, `{{examples}}`, `{{translations}}` (one line per locale; the English one is listed first as context when present), `{{dictionaryPrompt}}`, `{{grammarPrompt}}`, `{{transcriptionPrompt}}`. The criteria are the roadmap's: phrase (dictionary form, orthography), grammar (correct, only allowed tags), transcription (matches the phrase, follows the rules), translation (correct, shortenable, separator correct, no explanations mixed in), notes (needed at all, shortenable), examples (needed, removable, shortenable).
- [ ] Review reply schema (structured output): per field `{ok: bool, suggestion: string, reason: string}` for phrase, grammar, transcription, notes; `translations[]` of `{locale, ok, suggestion, reason}`; `examples[]` of `{index, action: keep|remove|shorten, suggestion, reason}`. A rewrite of the phrase is only valid together with its grammar and transcription (the three change as one unit). An invalid reply is retried with the existing correction mechanism, bounded like the item job.
- [ ] Job kind `review_vocabulary_item` (payload `{item_id}`; one job reviews the item in all its locales) is registered with the job queue; it reads the item, calls the review purpose once, stores the result in a new table `vocabulary_reviews` (item id, the phrase reviewed as the stale guard, the reply JSON, status `open|applied|dismissed` per proposal, created time), replacing the item's previous open review. An item gone or changed meanwhile skips the job like the item jobs do.
- [ ] `POST` endpoint queues one review job per item of a vocabulary list (items without a pending review job); a per-item variant queues one. Both respect the existing jobs permission checks.
- [ ] GUI: a `Review` button on a vocabulary list (queues the jobs, shows them in the Jobs menu like item jobs) and a per-item review indicator/dialog that lists the proposals field by field (current value, suggestion, reason) with Apply and Dismiss per proposal and for all. Strings in English and Polish (i18n).
- [ ] Apply is guarded: refused with a clear message when the item's phrase differs from the reviewed one. Applying a phrase proposal writes phrase, grammar and transcription together (existing `RewritePhrase`); the other proposals use new overwrite methods on the store (grammar, transcription, translation/notes, examples remove/replace), each under the same item-gone/phrase-changed guards.
- [ ] Tests: snippet round trip (store, admin API, rendering with and without it), config fallback to the `vocabularyItem` model, prompt rendering of all placeholders, reply parsing and rejection reasons, job with a fake store and fake Ollama (proposals stored, stale item skipped, new review replaces the old one), apply methods (including guards), endpoint queueing, frontend component test where a pattern exists. All without a real LLM.
- [ ] Verified on the dev cluster with at most 3-4 real Ollama calls in total (prompt-eval plus one end-to-end job), after checking the dev queue is empty.

## Approach

Ordered plan, each step a visible artifact reviewed with the user before the next:
1. Dictionary-form snippet end to end: schema column, `LanguageSections`, `sections.go`, `itemprompt.go` placeholder, admin API and form (`admin.go`, `admin-app.js`), i18n, `snippet/dictionary.txt` in prompt-eval plus sync. Visible: the third snippet in the admin form.
2. Purpose `reviewVocabulary`: config, Helm values, `ValidKinds`, `purposeDefault` with the `vocabularyItem` fallback, placeholders, admin list; prompt `review-vocabulary.txt` and the reply schema written in prompt-eval (with a small test file there) and synced; `ai.ReviewItem` call (render, one structured call, validate, correction rounds) with unit tests. Visible: prompt in admin, unit-tested call.
3. Persistence and job: `vocabulary_reviews` table and store, `review_vocabulary_item` handler registered in main.go, queueing helper, tests with fake store and fake Ollama.
4. Server endpoints (queue for list/item, read the open review, apply/dismiss) and the store overwrite methods with guards, tests.
5. GUI: Review button, proposals dialog, i18n, wiring of the Jobs menu; screenshot check on dev (Playwright, 1280 and 1024 px, an RTL list).
6. Dev deploy (`task deploy-phraseforge`), prompt-eval run and one end-to-end job against the current model (at most 3-4 Ollama calls total), docs (README, CHANGELOG), memory.

Key decisions: proposals are data, not writes, so a weak model can never damage items and a stronger one is simply a settings change; the item's reviewed phrase is the stale guard (same pattern as the item jobs); one call per item keeps prompts short and jobs cancellable; the new purpose reuses the existing prompt/provider/timeout machinery instead of a parallel config path. Alternatives considered: auto-apply (rejected by the user), one call per list (long lists, weak models), reusing the `vocabularyItem` purpose (cannot select a different model). Risks: step 4-5 is the largest (new overwrite methods and a dialog); a first-cut prompt will make some noisy proposals (accepted, prompts are optimised later); a 12b local model may not follow the structured review schema reliably, so the reply parser is lenient about unknown fields and strict about the three-fields-as-one-unit rule; the working tree already has many uncommitted changes from earlier work on main, which are left untouched.

## Affected Areas

prompt-eval/prompt/phraseforge/default (snippet/dictionary.txt, system/review-vocabulary.txt) and prompt-eval test files; phraseforge/internal/config (config.go, prompts.go, embedded prompts); phraseforge/internal/ai (ai.go, sections.go, itemprompt.go, new review call, itemjob payload helpers) and tests; phraseforge/internal/db/schema.sql; phraseforge/internal/vocabulary (reviews store, overwrite methods) and tests; phraseforge/internal/jobs (registration only); phraseforge/internal/server (admin.go, vocabulary.go, routes, static js and templates, layout.html if the Jobs menu needs it); phraseforge/internal/i18n/i18n.go; phraseforge/main.go; phraseforge/k8s/configmap.yaml; phraseforge/README.md and CHANGELOG.md.

## Out of Scope

Reviewing texts and dialogs (`phraseforge-text-dialog-review-job`); models lists; auto-applying; prompt quality tuning beyond a working first cut (`phraseforge-usage-prompts` style follow-up); writing dictionary-form snippets for any language; changing the item or generation jobs; committing (the user commits manually).

## Implementation Notes

1. Step 1, dictionary-form snippet (done): prompt-eval gets `default/snippet/dictionary.txt` (generic) and sample snippets for deu, arb, cmn and fin under `lang/<lang>/snippet/dictionary.txt` as a scaffold for tests; `lib/prompts.js` knows the `dictionary` kind and `dictionaryPrompt`, `lib/correction.js` renders it; synced into phraseforge with `npm run sync-prompts` (`check-sync` passes). Go: `dictionary_prompt` column (idempotent ALTER in schema.sql), `LanguageSections.DictionaryPrompt`, `{{dictionaryPrompt}}` in `renderItemPrompt`/`renderSnippets`/`usesSnippets`, `PromptPlaceholders`, `config.DefaultDictionarySnippet`, admin save/import and `snippetDefaults.dictionary`, the third row kind in the admin Languages tab, en/pl strings. The default prompts do not use the placeholder yet (the review prompt will, step 2), so behaviour of existing jobs is unchanged.
2. Step 2, purpose and call (done): purpose `review_vocabulary` / config key `reviewVocabulary` (`config.ReviewVocabulary`, defaults numCtx 8192, timeout 1800, 3 attempts, provider and model blank; `purposeDefault` fills a blank provider or model from `vocabularyItem`, so an admin LLM row or config.yaml with a stronger provider changes only this purpose); added to `ValidKinds`, the `llm_prompts` kind CHECK in schema.sql, `PromptPlaceholders`, the admin kind label (en/pl) and k8s/configmap.yaml (prompt copied from the default, provider/model blank). Prompt `system/review-vocabulary.txt` and the reply schema live in prompt-eval (suite `review-vocabulary/`: promptfoo config, 4 cases, `lib/review-vocabulary.js`, `npm run review-vocabulary[:smoke]`; sync-prompts checks schema, prompt and num_ctx). `ai.ReviewItem` (internal/ai/review.go): one structured call with correction rounds; reply parsed into flat `ReviewFinding`s (field phrase/grammar/transcription/translation/notes/example, action replace/remove/comment, locale, example index, current, suggestion, reason). Rules: a phrase suggestion must come with a grammar and a transcription suggestion for each the item has and the language keeps (else a correction round); then grammar and transcription ride on the phrase finding; checks for a field whose language snippet is missing (dictionary form for phrase, grammar, transcription) are ignored; notes with ok=false and no suggestion mean remove; unknown locales, example numbers and over-long example suggestions are ignored; reasons are capped at 300 characters. No Ollama call was made in this step.
3. Step 3, persistence and job (done): table `vocabulary_reviews` (schema.sql, `item_id` primary key referencing `vocabulary_items(id)` with cascade, `phrase` reviewed, `findings` jsonb, `response` jsonb, `created_at`; one row per item, a new review replaces it). `vocabulary.Store.ReviewSource` (phrase, grammar, transcription, language, examples, locales with a translation or notes), `SaveReview` (under `lockItemIfStill`, so a gone item is `ErrItemNotFound` and a changed phrase `ErrItemChanged`) and `GetReview`. `ai.HandleReviewItem` for job kind `review_vocabulary_item` (payload `{item_id}`, built by `ai.NewReviewJob`): reads the item, one `ReviewItem` call, stores the findings with `status: open` (an empty review is stored too), gone/changed ends the job as skipped. The store is set with `Service.SetReviewStore` (not a `New` argument, to keep the existing constructor calls) and adapted in main.go (`reviewStore`), the handler is registered there. Not done here by design: queueing for a whole list, skipping items that already have a pending review job, and reading the review over HTTP (step 4).
4. Step 4, endpoints and apply (done): `vocabulary.Store` gets `ListReviews` (per item: open/total findings, stale), `DismissReview` and `ApplyReview` (internal/vocabulary/review_apply.go) with the finding type `vocabulary.ReviewFinding` (same JSON keys as `ai.ReviewFinding`, pinned by a test). `ApplyReview` runs in one transaction under the review row lock and the item guard (the item must still hold the reviewed phrase: `ErrItemChanged` otherwise); each finding is guarded by the value it was about (an edited value is a `conflict`, nothing is written and the finding stays open); examples are found by their text, not their number; non-phrase findings go first and the phrase rewrite last (it may merge into an existing phrase, the survivor keeps its own data where it has some); a rewrite carries grammar and transcription as one `retargetPhrase`; afterwards the review follows the item's new phrase; remarks (`comment`) are `not_applicable`. `jobs.Service.ActiveItemIDs` lists items with a pending or running job of a kind. HTTP (internal/server/review.go, all behind CanEdit of the list's language): `POST /vocabulary/{id}/review` and `POST .../items/{position}/review` queue one job per item without a waiting one (`{enqueued, alreadyQueued}`), `GET /vocabulary/{id}/reviews` (`{reviews, pending}` for the list), `GET .../items/{position}/review`, `POST .../review/apply` and `.../review/dismiss` with `{"indexes": [...]}` (positions in the findings array; none = every open finding), which answer `{results, review}`. Errors: 404 no review/item, 409 stale review, 400 bad index or body, 403 no edit right.
5. Step 5, GUI (done): vocabulary view page (editors only): a Review button queues the list, a Review column per item (Review link; "Reviewing…" while a job waits, polled every 8 s; "N open" / "Reviewed" / "Outdated" opens the dialog); the dialog (pf-dialog `showContent`, built with the DOM API because proposals are model output) lists each proposal with the current and suggested value, grammar and transcription of a phrase rewrite, the reason, Apply and Dismiss per proposal, Apply all / Dismiss all open, Review again; applied and dismissed ones are dimmed with their status; source-language text keeps the list's script direction; a conflict or stale review is explained; closing reloads the view when something was applied. en/pl strings, styles in layout.html.
6. Step 6, docs (done): README (purpose, snippet, API), CHANGELOG. Not done by design: the real model verification budget was not used by me; the user's own GUI test queued about 50 real reviews on gemma4:12b (about 20 finished, 1 failed, the rest cancelled by the user's request because the machine was starved of memory); those jobs were deleted on request. Production Helm values (jdp-helm repo) do not carry `reviewVocabulary` yet; the compiled default applies.
