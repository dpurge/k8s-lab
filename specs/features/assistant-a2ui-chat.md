## Problem / Motivation

The assistant's chat shows only text: a conversation runs a workflow, and its messages are plain text of kind `text`, `question`, `result`, `error` or `info`. The user wants the chat to show real interfaces (forms, choices, tables, media) that a model composes on the fly, and to answer back through them, using the A2UI protocol (Agent-to-User Interface) so the same messages work with any renderer. They also want the chat to be driven by an orchestrator: one conversation entry point that decides, for each request, which of the assistant's workflows should handle it, and lets workflows act as subagents. This is the first step of a chat that is a catalogue of components later; the shared component library (`shared/ui`, spec `shared-ui-lit-library`) is its foundation.

Decisions confirmed by the user (2026-10-21):
- Protocol version: A2UI v1.0, the candidate for stable (the reference's own README names v0.9.1 as the current production release; v1.0 renames client and server to renderer and agent, lets `createSurface` carry the whole UI, and prefixes bindings with `@path`, `@call` and `@index`). The vendored schemas and the `web_core` version are pinned, so a change in the candidate shows up as a deliberate upgrade.
- Renderer: our own components built on the `dp-*` library, using only the framework-free `@a2ui/web_core` (message processing, the surface and data models, binding, function evaluation, schema validation), not the official Lit components.
- Media: images, video and audio come from `data:`, the assistant's own origin, and an optional configured list of allowed hosts (empty by default); nothing else.
- A subagent is one of the assistant's own workflows. Remote A2A agents are not part of this feature, though the delegation interface is kept small enough to add them later.
- All primitives of the specification: the 18 components and 14 functions of the v1.0 basic catalog, data binding, template children, actions, validation checks, the renderer's error reporting, and the bidirectional function-call messages (`callRendererFunction` with `rendererFunctionResponse`, and `callAgentFunction` with `agentFunctionResponse`), which the user asked to include on 2026-10-21 when approving this spec.

What the reference gives us (read 2026-10-21): the v1.0 specification under `specification/v1_0` (agent-to-renderer messages `createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface`, `callRendererFunction` and `agentFunctionResponse`; renderer-to-agent `action`, `error`, `callAgentFunction` and `rendererFunctionResponse`); the basic catalog `catalogs/basic/v1/catalog.json` (Text, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Divider, Modal, Button, CheckBox, ChoicePicker, TextField, DateTimeInput, Slider; functions and, email, formatCurrency, formatDate, formatNumber, formatString, length, not, numeric, openUrl, or, pluralize, regex, required), which embeds the model's design `instructions`; `@a2ui/web_core` 0.14.0 on npm (Apache-2.0, exports `./v1_0`); a conformance suite and an explorer with examples; and an orchestrator sample (Python, ADK and A2A: an LLM call on every request routes to one expert subagent). The reference warns that any UI definition from an agent is untrusted input.

## Acceptance Criteria

Renderer (in `shared/ui`, loaded on demand: a separate chunk, never part of `dp-core`)
1. `@a2ui/web_core` is a pinned npm dependency of `shared/ui`, and the v1.0 JSON schemas (`agent_to_renderer`, `renderer_to_agent`, `common_types`, the basic catalog) are vendored under `assistant/schemas/a2ui/v1_0/` with the upstream commit recorded next to them. A feasibility spike comes first and reports the size of the chunk and whether `web_core` runs under Node and jsdom for tests; if it does not fit, the slice stops and reports.
2. `dp-a2ui-surface` takes v1.0 agent-to-renderer messages and creates, updates and deletes surfaces; it keeps each surface's data model; it resolves `@path` bindings, `@index` template children and `@call` function calls reactively, so a data model update redraws only what depends on it.
3. All 18 basic-catalog components render, each built from `dp-*` blocks and themed only by the design tokens (light and dark): Text, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Divider, Modal, Button, CheckBox, ChoicePicker, TextField, DateTimeInput, Slider.
4. All 14 functions evaluate as the catalog defines them, including `ValidationResult` from `required`, `regex`, `length`, `numeric` and `email`, `formatString` with its interpolation, and `openUrl`, which needs a user gesture.
5. Form controls (TextField, DateTimeInput, CheckBox, ChoicePicker, Slider) are native elements in the page's own DOM inside the component, two-way bound to their data-model path, so input methods work (the library's IME rule): a Chinese and a Japanese composition and the assistant's own IME-less typing are checked in a real browser in the TextField.
6. Actions: a Button's `event` action sends the renderer-to-agent `action` message with its context resolved against the data model (and its `userMessage` when there is one); a function-call action runs in the renderer; `checks` on inputs and buttons disable the button and show their messages; a renderer problem (unknown component, invalid message, a binding that does not resolve) is reported as a renderer-to-agent `error` and shown as a visible placeholder, never as a crash.
6a. Function calls, renderer side: `callRendererFunction` is executed against the surface's root data context (or an isolated empty one when it names no surface) and answered with `rendererFunctionResponse` carrying the same `functionCallId` and either a value or an error; the renderer refuses, with an error response and not by executing, a function that is unknown, from an unregistered or missing `catalogId`, `rendererOnly` or one that `requiresUserActivation` while no user gesture is present, or whose arguments fail the schema; a function marked `agentOnly` cannot be bound to a component property. `callAgentFunction` sends a call to the agent, matches `agentFunctionResponse` by `functionCallId`, and times out with an error after a configured time; a response that matches no call is ignored and reported.
7. Untrusted UI: Text markdown is sanitized (no raw HTML, no `javascript:` links); Image, Video, AudioPlayer and `posterUrl` accept only `data:`, same-origin and the configured hosts, and a blocked URL shows a placeholder with the reason; `openUrl` opens only `http` and `https` with `noopener noreferrer`; the number of components, their depth and the size of a message are limited, and a message over a limit is rejected with an error.
8. Conformance: every example of the v1.0 basic catalog in the reference renders without error as a test fixture, and the renderer-relevant cases of the reference's conformance suite pass (which cases apply is established in the first renderer slice and listed in Implementation Notes).
9. A gallery page in the assistant (a hash route kept for development) shows each component with its reference example, in light and dark, at 1280 and 390 px, with the messages that produced it visible beside it.

Backend (Go, in `assistant`)
10. A conversation message can carry A2UI: a new kind `ui` with a JSON payload column (migration, `chat.Message`, `GET /conversations/{id}/messages`, `schemas/api/openapi.yaml`, tests), delivered by the polling the chat already does; the user's answers through the UI are stored as messages of kind `ui_action`.
11. Every agent message is validated before it is stored: against the vendored JSON schemas and the catalog (component types and properties), then the integrity rules (a root, unique ids, every referenced child exists, no cycles, `allowedParents` and `allowedChildren`), and the limits of criterion 7. An invalid message is not stored; the error names the component and property (walking the `jsonschema/v6` error causes to the leaves, per the memory log). A rejected message is counted in a metric.
12. `POST /api/v1/conversations/{id}/ui-events` accepts the renderer-to-agent `action` and `error` messages, rejects an unknown surface or component, stores the event, and delivers it to the workflow as the user's turn with the structured action (and shows its `userMessage`, if any, as the user's bubble).
12a. Function calls, agent side: a workflow can call a renderer function (the engine emits `callRendererFunction` as a `ui` message with a fresh unique `functionCallId`, and the answer arrives through `ui-events` as `rendererFunctionResponse` and is returned to the workflow as that call's result, or as an error on a refusal or a timeout); the renderer can call an agent function (`callAgentFunction` arrives through `ui-events`, is checked against a registry of agent functions with their argument schemas and `allowedCallers`, and is answered with an `agentFunctionResponse` as a `ui` message). The assistant has a small catalog of its own for the functions that the basic catalog does not cover, with at least one function of each direction that is useful, not a stub (for the renderer: the size of the viewport; for the agent: the list of the workflows a user can start). Calls are limited in number per turn and in time; a call with a duplicate `functionCallId` or no pending counterpart is rejected.
13. Reopening a conversation re-renders its surfaces by replaying its `ui` messages in order: updates apply, a deleted surface stays deleted, and a surface keeps the values the user entered if the agent has not changed them.
14. A workflow `ui-demo` that needs no model emits scripted surfaces covering the 18 components, and a form whose submit action produces a result message, so the interface can be tried by hand without the laptop's model (as `hello` does for text).

A model composes the UI
15. A workflow may declare that it can show UI (`ui: {catalogs: [...]}`); the engine then adds the catalog's embedded `instructions` and the component schemas to the prompt, accepts A2UI messages in the model's reply, validates them as in criterion 11, and, when they are invalid, retries with the error within the workflow's existing `max_retries`.
16. Tested with a scripted fake model for every path (valid UI, invalid then corrected, invalid until the retries run out, an action returning to the workflow); real model calls are budgeted: at most three, on the laptop, after the dev queue is checked.

Orchestrator
17. A workflow may declare `intents` (a short description of what it handles and example requests), and the assistant lists them as a registry the orchestrator reads; a workflow with no `intents` is not offered.
18. The engine can delegate to a child workflow (a subagent): it runs with its own state and limits, its questions, answers, results and UI appear in the same conversation, its result returns to the parent, the depth is limited, its model calls and tokens count towards the parent's budget, and the trace shows the delegation.
19. An `orchestrator` workflow makes one model call per user message that maps it to a registered workflow, or answers itself, or asks one clarifying question; it sees the registry in its prompt, and its choice and reason are recorded in the trace and shown in the chat as a short info line. Tested with a scripted model for each route, the no-match path, a delegation that asks the user something, and the depth limit.
20. The chat shows which workflow is handling the current turn.

All
21. Each slice ends deployed on the dev cluster and checked in a real browser at 1280, 1024 and 390 px, light and dark, with no console errors; the assistant's Content-Security-Policy is extended only by the configured media hosts (config key `a2ui.media_hosts`, environment `ASSISTANT_A2UI_MEDIA_HOSTS`, comma-separated, empty by default) and a test proves nothing else changes in it.
22. Documentation: `specs/tech-stack.md` (new dependencies and the vendored schemas; a gated constitution update when implementation starts), the assistant's README and CHANGELOG, the OpenAPI file, and the library README's note on loading catalog chunks on demand.

## Approach

Memory consulted: a2ui|orchestrat|csp|jsonschema|workflow.*(tool|state) — 1 relevant entry (jsonschema/v6 hides error kinds behind "validation failed": walk the causes to the leaves, as `assistant/internal/workflow` `errorLeaves` does).

How it fits. A2UI is transport-agnostic, so the existing REST chat is the transport: the agent's A2UI messages become `ui` messages in the conversation, the renderer's `action` and `error` events go back through one new endpoint, and the workflow engine treats an action as the user's answer. The A2A transport of the reference is not needed.

On the page: `dp-a2ui-surface` (Lit, in an on-demand chunk built by the same esbuild step, so the chat loads it and Tasks and Usage never do) wraps `web_core`'s `MessageProcessor` and surface models. Each catalog component is a Lit element that renders in the light DOM from `dp-*` blocks, so native controls stay the page's own and the IME rule holds; its state comes from `web_core`'s signals. The assistant's `as-chat-thread` shows a surface in the thread for each group of `ui` messages. The chunk is the first user of "catalog components load on demand", which is also where a later custom catalogue goes (`web_core` supports mixing catalogs on one surface).

On the server: a new Go package `internal/a2ui` holds the vendored schemas, the validator (the `jsonschema/v6` dependency already in `go.mod`) and the integrity and limit checks; `internal/chat` stores and replays `ui` messages and takes the events; the workflow engine gets the optional `ui` declaration, the catalog instructions in the prompt and the retry-on-invalid loop; delegation is a new engine capability (a tool and a trace record) that the `orchestrator` workflow uses.

Ordered slices; each ends deployed and checked, and I ask for a go-ahead between them:
1. A1, spike: add `@a2ui/web_core` to `shared/ui`, vendor the schemas, bundle a small renderer into a chunk, run it under jsdom with a reference example, and report its size. If this does not work, stop and report before anything else is built.
2. A2, renderer core and layout: `dp-a2ui-surface`, data model and binding, templates, function evaluation, and Text, Row, Column, List, Card and Divider; the gallery page; the reference examples and conformance cases that apply, as tests.
3. A3, inputs and actions: Button, TextField, CheckBox, ChoicePicker, DateTimeInput and Slider, two-way binding, `checks`, the `action` and `error` messages, the validation functions; the IME check; and the renderer's side of the function calls (`callRendererFunction` and its response, `callAgentFunction` and its timeout).
4. A4, the rest of the catalog and untrusted-input rules: Tabs, Modal, Icon, Image, Video and AudioPlayer, the media allowlist and the CSP extension, `openUrl`, markdown sanitizing, the limits.
5. B1, the server side of the chat: the migration, the `ui` and `ui_action` kinds, validation, the events endpoint, replay, the agent's side of the function calls with the assistant's small catalog, the `ui-demo` workflow, and the thread showing surfaces: the first slice where a conversation shows A2UI end to end, with no model.
6. B2, a model composes UI: the `ui` declaration, the prompt, validation and retry; scripted-model tests and the budgeted real calls.
7. C1, delegation in the engine and the `intents` registry.
8. C2, the `orchestrator` workflow and the chat's routing display.

Cost, stated plainly: eight slices; the renderer (slices 1 to 4) is the largest part, as it implements 18 components, 14 functions and the binding rules; slice 1 is a bounded check, not a promise that the rest will fit. Every slice adds tests first and keeps the suites green.

Alternatives considered: the official `@a2ui/lit` renderer (faster and conformant, but its own look and its own shadow-DOM controls, which would have to be restyled and would not follow the IME rule); A2A subagents as in the sample (not needed for workflows in one process, and a security model of their own); version v0.9.1 (stable, but the user chose v1.0).

Risks: v1.0 is a candidate and may change (mitigated by pinning and by vendoring the schemas); `web_core` pulls in zod and signals, so the chunk may be large (slice 1 measures it); the model must produce valid A2UI reliably (the validate and retry loop and the catalog's `instructions` help, and the real-call budget limits what can be proven on the laptop's model); a rendered surface is untrusted input (criterion 7 and the limits); the engine change for delegation is the riskiest server change (one slice of its own, with the depth and budget limits).

The function-call messages map onto the REST chat the way the protocol's own request-response guide describes: the agent's `callRendererFunction` arrives as a `ui` message, the renderer executes it and POSTs the `rendererFunctionResponse` to the events endpoint, and a `callAgentFunction` is POSTed the same way and answered with an `agentFunctionResponse` message. Which functions each side may call is the catalog's `allowedCallers`, enforced on both sides.

## Out of Scope

- Remote A2A agents, the A2A transport and agent cards.
- A custom component catalogue of our own (only the extension point is kept open; the user will want one later).
- Protocol versions other than v1.0.
- User management and roles (postponed by the user).
- Changing how the chat polls (no streaming or WebSocket).
- Visual redesign of the chat beyond showing surfaces and the routing line.

## Implementation Notes

### A1 spike (done)

`@a2ui/web_core@0.14.0` added to `shared/ui` (exact pin). Checked with a throwaway script (scratchpad, not in the repo), plain Node, no jsdom needed:

- `@a2ui/web_core/v1_0` imports; `MessageProcessor([basicCatalog], onAction)` processes `00_simple-text` and `00_interactive-button` from the a2ui examples; surfaces are created and `componentsModel.get(id)` returns every component.
- `callRendererFunction` goes through `processMessagesAsync`; the message shape is `{callRendererFunction: {functionCallId, callFunction: {catalogId, call, args}}}`. The processor answers with `rendererFunctionResponse` and enforces `allowedCallers` (`formatNumber` from the agent returned `INVALID_FUNCTION_CALL ... rendererOnly`).
- An update for an unknown surface throws `Surface not found for message: <id>`, so the client must catch it and report an `error` message.
- esbuild bundle (minified ESM, on-demand chunk candidate): with `basicCatalog` 449 KB raw / 123 KB gzip; processor only 254 KB raw / 66 KB gzip.

Fits the plan: loaded only when a chat shows a `ui` message.

### A2 renderer core and layout (done; deployed to dev)

Built in `shared/ui/src/a2ui/`, as a second stable esbuild entry (`dist/a2ui.js`, shares Lit with `dp-core.js`; the gallery is a third entry, `dist/a2ui-gallery.js`). `dp-core.js` is unchanged (26.5 KB, 7.3 KB gzip); `a2ui.js` is 436 KB raw, 118 KB gzip, mostly web_core's zod schemas.

- `dpCatalog`: web_core's basic catalog (same id, schemas and 14 functions) with our elements as implementations; `createProcessor(onClientMessage)` wraps `MessageProcessor`. web_core does not export `toWebComponentImplementation`, so `catalog.ts` has a two-line local helper.
- `DpA2uiElement` (base.ts) extends web_core's `A2uiLitElement` (resolved props as signals, templates, `renderNode`), renders in the light DOM and applies `weight` as flex-grow. Component CSS sits next to the component and is adopted per tag by `A2uiLitElement`.
- Components so far: Text (plain text only: markdown waits for the sanitizer in A4, so the reference examples' `#` headings show literally), Row, Column, List, Card (draws `dp-card`), Divider. `dp-a2ui-surface` follows a `SurfaceModel`'s root.
- The v1.0 `List` schema has no `listStyle` (the reference's own element is ahead of its schema), so it is not supported; `Text.variant` is only `caption` or `body`.
- Bindings in v1.0 are `{"@path": ...}`; a template child list is `{componentId, path}`.
- Found in the browser, not by tests: the assistant's CSP (`style-src 'self'`) blocks a `style="..."` attribute, which a Lit `style=${...}` binding writes. CSSOM assignment (`this.style.flex = ...`) is allowed. Components therefore use classes or CSSOM, never a style attribute (a test for List alignment guards it).
- Gallery: `dp-a2ui-gallery` draws the 7 bundled reference examples (copied unchanged to `src/a2ui/fixtures/`, commit recorded in its README) with their messages beside them; the assistant route is `#/gallery`, which imports the chunk on demand. Checked on dev at 1280, 1024 and 390 px, light and dark: 7 of 7 surfaces draw, no horizontal overflow, no console errors.
- Tests: 164 in `shared/ui` (17 new: 7 components, bindings, templates, root lifecycle, 7 reference examples, gallery); assistant frontend 287; `go test ./ui` ok.
- Reference examples that need only these six components: 7 of 40. The rest come with their components.

Conformance (criterion 8): the reference suite's `core/` cases test web_core itself (processor, expressions, data model), which we use unchanged, so they are not re-run. Run against our catalog: the 55 `evaluate_function` cases of `core/functions.yaml` that name no surface (54 apply to v1.0; the `_v0_9` case is skipped; the unversioned cases were written for v0.9, where validation functions return a boolean, so the test compares the v1.0 `ValidationResult.valid`); 8 multi-catalog `surface` cases do not apply to one catalog. From `core/accessibility.yaml`: label, description, live and hidden (plain and bound) are plumbed to ARIA attributes on every component and tested for Text and Column; the interactive cases (Button, TextField, CheckBox, ChoicePicker roles and `checked`) come with A3. Not applicable here: `validator_*`, `node_resolution`, `data_*`, `rpc_functions` (web_core's own, re-tested in A3 for our wiring).
- Caption text has the body's size and only a muted colour (user request, from the Row example); `--dp-a2ui-caption-size` and `--dp-a2ui-caption-color` change it.
- Tests: 221 in `shared/ui`.

### A3 inputs, actions and renderer-side calls (done; deployed to dev)

In `shared/ui/src/a2ui/`: Button (draws `dp-button`; `borderless` has no dp-button look and is drawn as the default), TextField (shortText, longText, number, obscured), CheckBox, Slider (`steps` = equal divisions), ChoicePicker (radio or checkbox, list or chips, optional filter), DateTimeInput (date, time, datetime-local; ISO text in the model). All 18 minus Tabs, Modal, Icon, Image, Video and AudioPlayer (A4).

- Controls are native elements in the page's own DOM (light DOM, labelled through `dp-field`), two-way bound through web_core's `setValue`. Text inputs and the filter write to the model on `input`, but not while `isComposing`; the model is written on `compositionend`.
- Checks: a failed `checks` rule shows its message under the field (`role=alert`, `aria-invalid`) and disables a Button with the same rule; the Button's tooltip carries the message. In v1.0 the validation function's own `ValidationResult.message` wins over the rule's `message` (the rule's is the fallback for a boolean result), so the text is "This field is required." and not the example's "Email is required".
- `createClient({send, callTimeoutMs})` (`client.ts`) is the renderer's side of the conversation. Everything sent to the agent is a `{version, action | error | callAgentFunction | rendererFunctionResponse}` message through `send`: actions get a timestamp; a message the processor rejects becomes an `error` (VALIDATION_FAILED with the path, or a generic code) and later messages are still handled; errors a surface reports are forwarded; a component type the catalog lacks is reported (VALIDATION_FAILED, path `/components/<i>/component`) and drawn as a visible note, siblings unaffected; `callRendererFunction` is answered by web_core with a `rendererFunctionResponse` (refusals tested: `rendererOnly`, unknown catalog, unknown function); `callAgentFunction` has a time limit and resolves or rejects from the matching `agentFunctionResponse`; an answer to a call nobody made is reported (UNKNOWN_FUNCTION_CALL) and ignored.
- Deviation from criterion 6: a binding that does not resolve is a *warning* in web_core (`MISSING_DATA_BINDING`), normal while an agent is still filling the data model in, so it goes to the console and not to the agent. A failing call inside a binding is an error and is sent.
- Not yet covered: a renderer function that an agent may call and that returns a value (no basic function allows an agent as caller; the assistant's own `viewport` function arrives with B1), the `requiresUserActivation` gesture for `openUrl` (A4), `userMessage` on actions (web_core passes it when the action has one; shown as the user's bubble in B1).
- Real browser (Chromium, dev, 1280/1024/390 px, light and dark; 17 of 17 examples draw, no console errors, no horizontal overflow): typed text and a click send the expected `action` with its bound context. Input methods were driven through Chromium's own protocol (`Input.imeSetComposition` and `Input.insertText`): during composition the field shows the composing text ("にほん"), the commit gives "日本語", and a Chinese commit appends "你好". Not done: a real OS input method (macOS Kotoeri, Windows IME) and Safari/Firefox.
- Known upstream behaviour: web_core 0.14.0 reports an EXPRESSION_ERROR when `and` or `or` has operands that are calls to `required`, `email` or `length` (ValidationResult functions); `returnType` does not help; operands that are paths work. The check counts as failed, so a Button with such a rule stays disabled. It affects the examples `09_login-form` and `32_advanced-form-validator`, which the tests list as known errors. It matters for B2: a model that writes such a rule gets an error back. The reference's own conformance cases pass only because they call the functions directly.
- Inputs are styled by the components (border, radius, padding, tokens), because the page styles its own controls and a model's form should look alike in every app; Text inherits its colour (so text inside a primary Button stays readable).
- Gallery: live (type, click) with a "Sent to the agent" log per example; 17 examples (the 10 new ones are the examples whose components now exist).
- Tests: 257 in `shared/ui`.

### A4 the rest of the catalog and the untrusted-input rules (done; deployed to dev)

- Components: Icon (59 catalog names as Material SVG paths, generated; `{svgPath}` is only a path's `d` attribute), Tabs (a `dp-tabs` bar; the selection is the viewer's, not the data model's), Modal (the trigger in place, the content in a native `<dialog>`), Image (variants and fit; a blocked or failed image draws a note with the reason), Video and AudioPlayer (native controls, never autoplay, poster checked). All 18 basic components are implemented; a test pins the list.
- Text markdown (`markdown.ts`, own parser, no new dependency): headings, paragraphs and line breaks, bold, italic, `code`, code blocks, lists, links. It builds DOM through Lit templates and never parses HTML, so `<script>`, event handlers and `<iframe>` are plain characters. A link is a link only for http and https (new tab, `noopener noreferrer`); `javascript:`, `data:`, `mailto:`, protocol-relative and other addresses leave the label unlinked; an image is its alt text. Pathological inputs (50,000 `*`, `[`, backticks, long heading lines) run in well under the 8 s test bound.
- Media policy (`media.ts`): `data:` of the matching kind, this origin, and https on a configured host (exact host and port; no subdomains, no userinfo tricks); everything else is refused with a reason. Hosts reach the page through `GET /a2ui-config.json` (the gallery route sets them before drawing).
- Server: `ASSISTANT_A2UI_MEDIA_HOSTS` (the spec's config key `a2ui.media_hosts` is this environment variable: the assistant has no config file) is parsed as bare lower-case hosts with an optional port; anything else (scheme, path, wildcard, space, quote, semicolon) stops startup, since the value is written into the policy. Deviation from criterion 21 ("only the hosts extend the policy"): the base policy gains `media-src 'self' data:` for same-origin and `data:` video and audio, which `default-src 'none'` would otherwise block; with no hosts configured that is the only change, and with hosts the only further change is the hosts on `img-src` and `media-src`. Tests pin the exact policy string both ways, for the page, an asset and the config endpoint. OpenAPI documents the new route (the route-list test caught it missing).
- `openUrl` is our own implementation (web_core's also opens `mailto:` and `tel:`): http and https only, `noopener,noreferrer`. It runs only from a user's action (the Button), never from a binding, and an agent's `callRendererFunction` for it is refused.
- Limits (`limits.ts`; overridable in `createClient`): 256 KB per message, 500 components per message, 1000 per surface (replacing a component does not count twice) are rejected whole as `LIMIT_EXCEEDED`; nesting deeper than 20 levels and reference cycles are rejected by web_core as `RECURSION_ERROR`; nothing of a rejected message is kept.
- All 43 examples of the reference's basic catalog are bundled as fixtures and drawn by the tests and the gallery. Two report the known web_core error described under A3.

### B1 server side, first part: storage and validation (done; not deployed yet)

B1 is split into smaller steps. Done: the storage of `ui` messages and the validator. Open: the events endpoint, the engine and `ui-demo`, the agent's functions, the thread showing surfaces (below).

- Storage: `messages.ui jsonb`; kinds `ui` (assistant, an array of A2UI messages) and `ui_action` (user, the one message the page sent back); a CHECK keeps the two together (`ui` is set exactly for those kinds); `assistant migrate` upgrades an existing database (`ADD COLUMN IF NOT EXISTS`, constraints dropped and re-added). `chat.Message.UI` is omitted from the JSON of the other kinds; `GET /conversations/{id}/messages` and `openapi.yaml` describe it; `Store.AddUIMessage`. A conversation's last words show "(an interface)" for a `ui` message without text. jsonb keeps the content of the JSON, not its spelling (key order, spaces), so a page must not rely on either.
- `internal/a2ui` (new): the protocol's schemas are vendored unchanged under `schemas/a2ui/v1_0/` with the upstream commit in `SOURCE.md` (one adjustment in memory: the identifier patterns use `\p{XID_Start}` and `\p{XID_Continue}`, which Go regexps lack, so they are replaced by the covering Unicode classes). `Validator.Check` refuses a message that is too big, not JSON, not exactly one known kind, or invalid against its kind's schema; each component is checked against its own type's schema (the envelope plus the catalog's definition, closed with `unevaluatedProperties`), so one bad component is one report that names the component and property (`/updateComponents/components/1/...`: "unknown component type", "missing property", `"colour" is not allowed here`, wrong type, bad enum), not eighteen. Causes are walked to their leaves (`yamlschema.Leaves`), as the memory log asks.

Dangling references and a missing root are allowed while messages arrive in pieces and are asked for by `Finish()`. Child references are found by reading the catalog's own definitions (Child and ChildList properties, also inside Tabs and templates), not by a hardcoded table.

The basic catalog has no `allowedParents`/`allowedChildren`, so those rules are not applicable yet.

### B1 second part: events, the engine, `ui-demo` and the thread (done; deployed to dev)

Still open in B1: the agent's side of function calls with the assistant's own catalog (`viewport`, `listWorkflows`), the metric for rejected messages, and keeping entered values on replay.

- Engine to chat: a workflow's `ask_user` payload may carry `"ui"` (an array of A2UI messages), with or without words. `Service.TaskUpdated` posts the words as a question (none for an interface alone), then validates the interface against what the conversation has drawn (rebuilt from its stored `ui` messages) and stores it as one `ui` message. An invalid or incomplete interface is not stored; the conversation says `⚠ The interface was refused: <problems>`. With no validator configured it says it cannot draw interfaces. A new surface must be complete (a root) when its message group ends.
- Page to engine: `POST /api/v1/conversations/{id}/ui-events` (OpenAPI documented, 400 for an invalid or foreign message, 409 while the run works, 404, 502). The body is validated against the protocol's renderer-to-agent schema; an action must come from a component of a surface this conversation drew (unknown surface or component: 400); it is stored as a `ui_action` message shown as the user's turn (its `userMessage`, else `(name)`) and handed to the run as `{"ui_action": <action>}`, resuming a waiting run or starting a new one, the same path as a typed message (`Send` and `Event` share `currentRun` and `advance`). An `error` event is stored (shown as a note) and does not reach the run. `callAgentFunction` and `rendererFunctionResponse` get 400 "not handled yet".
- Demo: `workflows/ui-demo.yaml` plus the demo model (`internal/llm/demo/uidemo.go`): a tour of all 18 components on one surface, then a form whose Submit is disabled until the name is filled in; the run ends with a sentence made from the answers. Surface ids are random per run (an id is used once per conversation), so a conversation can run it again.
- Found by looking at it in a browser, not by the first tests: the page's renderer (web_core) refuses a component id that is not a UAX #31 identifier, while the protocol's schema only says "string": the demo used `text-card`, the server stored it, and the page showed nothing. The validator now refuses such ids with a message that says why, and a test pins it; the demo's ids use underscores.
- Page: `as-chat-thread` draws a `ui` message by loading `/ui/a2ui.js` on first need (and `/a2ui-config.json` for the media hosts), creating one renderer client per conversation, feeding it the A2UI messages one at a time, and showing a `dp-a2ui-surface` for each `createSurface` (a deleted surface disappears; a message that creates none leaves no row). Actions are POSTed to `ui-events` and the thread reloads; a refused action shows the server's reason. Errors from interfaces already in the history when the conversation was opened are not reported again at each reload. An interface followed by a `ui_action` is dimmed and inert. A renderer that fails to load is said in the thread and the rest still works.
- Checked in a real browser (Chromium, dev, 1280 px): a `ui-demo` conversation from a typed message to the final result: all 18 component types drawn in the thread, no unknown component, no console errors from the app; IME in the chat's TextField ("にほん" while composing, "日本語" after the commit); Submit disabled until the name is typed; the first interface inert after Continue; reopening the conversation redraws both interfaces (inert).
- Not done or not checked: 390 px and dark mode in the thread; typed values are not restored on reopening (criterion 13, "a surface keeps the values the user entered": it needs the page to send its data model with the action, designed next); Safari and Firefox.
- Tests: Go (`task test-assistant`, with the database, -race): `internal/a2ui` events and ids, `internal/chat` (ui posting, refusal, validator-less, events, busy, errors, duplicates), the whole flow through HTTP with the engine and the demo model (`app_engine_test.go`); frontend 298 (11 new for the thread, with a stand-in for the renderer chunk).

### B1 third part: function calls, the assistant's catalog and kept values (done; deployed to dev)

B1 is complete. The criteria it covers: 10 to 14 (the `ui`/`ui_action` kinds, validation, the events endpoint, replay with entered values, the agent's side of function calls, `ui-demo`), 12a and the metric of criterion 11.

- The assistant's catalog (`schemas/a2ui/assistant_catalog.json`, ours, not vendored): `viewport` (`rendererOrAgent`, an object `{width, height, pixelRatio, colorScheme}`) and `listWorkflows` (`rendererOnly`, a string, one line per workflow). The validator merges its functions into the document that stands for `catalog.json` (the protocol's `FunctionCall` refers to one `anyFunction` list), and judges which catalog a call names separately: a call needs a function of the catalog named by `catalogId`, and for `callRendererFunction` one the catalog lets an agent call (`allowedCallers` not `rendererOnly`). The catalog's id is `https://assistant.k8s-lab.local/a2ui/catalog.json`; a frontend test keeps the page's copy of the id, the function names, callers and return types equal to the document.
- Page to assistant (`callAgentFunction`): stored as a `ui_action` message (shown nowhere: the thread hides function traffic), answered by the assistant as an interface message holding an `agentFunctionResponse` (value, or an error `FUNCTION_NOT_FOUND` / `INVALID_FUNCTION_CALL`); the surface must exist, the call id is used once for the conversation, at most 10 calls between two messages of the user (a user's message or action starts a new turn); it does not move the run. The registry is `runAgentFunction` (`listWorkflows`).
- Run to page (`callRendererFunction`): a run's `ask_user` payload carries it under `ui`; the assistant gives every call a fresh id (a run cannot choose it, so an answer can only match a call the assistant made), at most 5 per interface; the page runs it and answers; the answer must match a call that is still waiting and is taken once (a duplicate or unknown id is a 400); it reaches the run as `{"ui_function_response": {functionCallId, value | error}}` if the run is waiting. A call not answered within `CallTimeout` (15 s) is answered by the assistant with `TIMEOUT` the same way; the timer is in the process, so after a restart a pending call is not timed out and the run waits for the user (accepted). An answer and a timeout of the same call cannot both be recorded (a mutex), and a late answer is refused.
- Page: `defineCatalog` and `createClient({catalogs})` (new in `shared/ui`, with `zod` declared as a direct dependency) let the assistant define `viewport` (the page's window and its theme) and `listWorkflows` (async: it asks the assistant through `callAgentFunction`; the value appears when the answer arrives). An async function runs once per distinct arguments, because the renderer evaluates a binding more than once. The thread reloads at once after a call to the assistant or an answer to a run's call, so neither waits for the next poll. Function calls and answers in the history are not replayed (replaying would run the function again and answer a call that was answered long ago).
- Kept values (criterion 13): an action carries the data model of the surfaces in `metadata.extensions.assistant_data_model` (the protocol's own extension point; the key must be an identifier and may not start with `a2ui_`); the page puts the values back when the conversation is opened again (an `updateDataModel` after the surfaces are drawn). A surface with a password field (`obscured` TextField) is never included, so such a value is not stored; a very large model (over 64 KB in all) and empty ones are left out. What is kept is what was entered when the user last acted; typing that was never submitted is not.
- `ui-demo` now has a state `device` between the tour and the form: the run asks the page for `viewport` with no words to the user, and the form's heading says "Seen from a 1100×900 window, light theme". The tour has a Text bound to `listWorkflows`.
- Metric: `assistant_a2ui_rejected_total{source="interface"|"event"}` counts messages the validator refused.
- Found while checking in the browser: replaying history re-ran the stored `viewport` call and re-answered it (a 400 and a console error at every reload), and the agent's stored answers made the page report an unknown call; both fixed by not replaying function traffic. The tour's data model lacked `chips`, which produced a binding warning; fixed.
- Checked in a real browser (Chromium, dev): the tour's Text shows the real workflow list asked of the assistant; the page answered the run's `viewport` call by itself and the form followed with the window's size; the submitted form (name and a chip) is restored after reopening; no console messages of any kind.
- Tests: Go (`task test-assistant`, database, -race) for the catalog in the validator, both directions of calls (answers, errors, duplicates, limits, timeout, a late answer, an answered call not timing out, the limit of five), the demo's flow through HTTP including the agent call, the metric and the counter; `shared/ui` 321 (6 new for `defineCatalog`, including a successful agent-called function); frontend 311.
- Still not checked: Safari and Firefox; an `obscured` field in a real conversation (unit-tested only).

### B2 a model composes the interface (mechanism done and tested with a scripted model; gemma4:12b did not compose one in the single real attempt)

- Declaration: `ui: {catalogs: [basic]}` on a workflow (JSON schema, `Workflow.UI`, lint). `Prompts.UIGuide` (from `a2ui.Validator.Guide()`, built from the catalog itself: rules, each of the 18 components with its properties, one complete reply; about 5 KB, under 1.5k tokens; a test keeps the example valid and caps the size at 8 KB) is added to the system prompt of every step of such a workflow. The basic catalog's own embedded `instructions` were not used verbatim: they are written for a different reply shape, and the guide has to fit a small context; its two ideas that matter (one `createSurface` message with the components and the data model, and checks inside the component) are in the guide.
- Validation and retry: after `ParseReply`, `Engine.checkInterface` refuses a reply whose `ask_user` payload has a `ui` that is not an array of valid A2UI messages (`a2ui.Validator.CheckInterface`: each message against the protocol and the catalog, then the whole for a root and missing children; problems are paths such as `ui[0]/createSurface/components/0/component`, at most eight and then "(and N more)"). The refusal goes back to the model as the `retry` of the same step, within the workflow's `max_retries`; when they run out the run fails with `retries_exhausted` and the last problem. A workflow without `ui` is not checked here (the chat checks when it shows it).
- A reused surface id is renamed in the conversation (`main` becomes `main-1a2b3c4d` in every message of the group), since a surface id is used once and a model writes `main` every time; this replaces the earlier rule that refused the second interface.
- Scripted-model tests (criterion 16): the guide reaches the prompt of a declaring workflow and not of others; a valid interface is accepted and comes out in the ask payload; invalid then corrected (outcomes retry, ok; the retry carries the problems and the refused reply); invalid until the retries run out (three calls, `retries_exhausted`); not an array, and no root; a workflow without `ui` is not checked; the user's action returns as the observation and the run goes on; an unknown or empty catalog list is refused at load.

### C1 delegation and the intents registry, C2 the orchestrator and the routing display (done; deployed to dev; scripted models only)

Criteria 17 to 20. No real model call was made in this slice.

- Intents (17): `intents: {description, examples}` on a workflow (JSON schema and `Workflow.Intents`); the registry the orchestrator reads is `EngineRunner.Intents()`, which lists the YAML workflows that declare them, so one without is never offered; `GET /api/v1/workflows` shows each workflow's `intents` (null when none). Declared for `hello`, `ui-demo`, `ui-compose` and `learn-topic`; not for `hello-live`, the built-ins or the orchestrator itself.
- Delegation (18), in the engine: a state with `delegate: true` may reply with the `delegate` action (`workflow`, `message`, optional `reason`); the step input then carries `delegates` (id, description, examples; an empty list at the depth limit) and the system prompt a short guide. The reply is refused, and the model told why, for a state that cannot delegate, a workflow that is not offered (the offered ids are named) or a run at the depth limit (default 2, `Engine.MaxDepth`). The child is a `Run` nested in the parent's (`Run.Child`, stored in the task's run snapshot and restored), started from the delegated message with its own state, limits and model tags; its steps continue the parent's numbering (`StepBase`) so one trace reads in order, each record carrying its workflow and depth (new columns `task_steps.workflow_id` and `depth`; the Step API and the admin trace show them, indented with `↳`); its tokens are capped at what the parent had left (`TokenCap`) and added to the parent's when it ends. A child that waits for the user keeps the parent waiting with the child's question (`Result.Workflow` says who asks) and the user's messages go to the deepest child; when it ends its final state returns to the parent as `{"delegate_result": {workflow, state}}`, a failure as `{"delegate_error": {workflow, reason, message}}`, and the parent goes on. A child whose workflow is no longer known fails the run. The child's questions, answers, results and interfaces appear in the conversation because they are the run's own asks.
- Orchestrator (19): `workflows/orchestrator.yaml` (tag `orchestrator`): one state `route` with `delegate: true`: delegate to the workflow that fits, or ask one clarifying question, or record an answer and finish; with a `delegate_result` or `delegate_error` it records one or two sentences and finishes. The model call per message is the route step; summarising a finished child costs one more call. `Result.Routed` and the ask's `routing` key carry the choice and the reason; the chat posts `→ hello: you mentioned "hello"` before the question, and the choice and reason are in the trace as the step's `delegate` action. The dev demo model plays the orchestrator by keywords (the dev `demo-hello` model has the tag `orchestrator`; `models.example.yaml` gives the tag to the GPU model).
- Chat (20): the conversation view has `handled_by`, the workflow of the deepest child while the run is waiting, running or pending (null otherwise); the thread header says "Handled by <workflow>".
- Tests with a scripted model (19): every route (to a workflow, no match answered by the orchestrator itself, a clarifying question), a delegated workflow that asks the user something and receives the answer, a result and a failing child coming back, the depth limit (refusal and an empty `delegates`), the token cap, refused targets corrected on retry, a state that may not delegate, the prompt for states with and without `delegate`, a stored and restored run with a child, the trace format; the whole thing through HTTP with the real engine and the demo model (routing line, handled_by, one trace numbered across both workflows, action on the child's interface); frontend (header, info line, trace labels).
- Checked in a real browser (dev): "please say hello to me" shows the routing line, "Handled by hello", the child's question, and after the answer the orchestrator's result and a header without a handler; "show me the interface components" is routed to `ui-demo` and its interface is drawn; no console messages.
- Not done: real-model routing (the budget was spent in B2; a model with the tag `orchestrator` is needed, see `models.example.yaml`); a child asking to be re-routed mid-conversation (the user's messages stay with the child until it ends); a restart while a child waits is fine (the run snapshot holds it) but a pending function call's timer is lost, as noted under B1.
