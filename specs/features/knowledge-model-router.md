## Problem / Motivation

Knowledge calls models through `shared/llm` with one provider per purpose (`chat`, `generateTitle`, `generateSummary`, `translate`), reads the embedding model through a separate client (`knowledge/internal/embeddings`), uses legacy camelCase config keys, has no fallback, no Vertex, and keeps no record of calls. Assistant and phraseforge already use `shared/router`: tagged models with priorities, a circuit breaker, providers ollama, openai, anthropic and vertex, a `models.yaml` ConfigMap, an `llm_calls` table, Prometheus metrics and admin pages. Knowledge must join, so the dev `task llm-*` tasks (`specs/features/llm-provider-tasks.md`, which names this feature as the step before knowledge joins them) can cover it.

Decisions by the user (2026-10-22):
1. Embeddings move into the router (a new embeddings API in `shared/router`). Qdrant stays supported; the user may later replace it with the Postgres vector extension, so producing an embedding must not depend on the vector store.
2. All of knowledge's config keys are renamed to snake_case now, per `specs/tech-stack.md` Naming conventions; a renamed key's old name is rejected at load with a message naming the replacement. This is a breaking change to `knowledge/k8s/configmap.yaml` and to the production Helm chart (outside this repo: documented, not changed).
3. Observability at full parity with phraseforge: table `llm_calls`, Prometheus metrics (knowledge has no `/metrics` and no Prometheus client today) and admin pages for usage, models and attempts built from the shared UI components.
4. The `llm-*` tasks cover knowledge as the last step.

KEY RISK, for the user's approval: an embedding fallback between different embedding models would silently corrupt a vector index (a different dimension, or a different vector space even with an equal dimension). Proposed rule (AC 14 to 18): a model in `models.yaml` declares an `embedding_space` and a `dimension`; knowledge names the space and dimension it needs; the router picks only models of that space, so fallback happens only between copies of the same model (for example `bge-m3` on a LAN Ollama and on the laptop); a reply whose vector length differs from the configured dimension is a failed attempt and is never stored; a provider type without an embeddings endpoint can never carry an embedding model. If this rule is wrong or incomplete, the index is corrupted without any error, so it needs the user's explicit approval before step 3.

## Acceptance Criteria

Configuration
1. Models are configured in `models.yaml`; its path comes from the new env var `KNOWLEDGE_MODELS_FILE`, default `/etc/knowledge/models.yaml`. Startup fails, naming the variable and the file, when it is missing or invalid. `knowledge/models.dev.yaml` is the committed dev file (Ollama on the laptop, reached as `host.docker.internal:11434`, as in the current `knowledge/k8s/configmap.yaml`).
2. Each of `chat`, `generate_title`, `generate_summary` and `translate` has a required, non-empty `model_tags` list (empty or duplicate tags are rejected). The old `provider` and `model` keys are rejected at load with a message naming them and the replacement. Startup fails when a purpose's tags match no model. Startup also fails when a model matching the purpose's tags has `options.num_ctx` smaller than the purpose's `num_ctx` (an ollama model only, as in phraseforge; a purpose without `num_ctx` is not checked).
3. Every config key is snake_case. The old camelCase name of each renamed key (Table A) is rejected at load with a message naming the file, the old key and its replacement; unknown keys in `config.yaml` are rejected naming the file and key (as phraseforge does). The keys already rejected today (`generate`, `prompts`, `<section>.baseURL`, and the env vars `CHAT_API_KEY`, `GENERATE_API_KEY`, `TRANSLATE_API_KEY`, `EMBEDDINGS_API_KEY`) stay rejected.
4. The `providers` block of `config.yaml` (ollama, openrouter, openai with `baseURL`, `firstTokenTimeoutSeconds`, `idleTimeoutSeconds`) is removed: providers, their `base_url` and the streaming limits (`first_token_timeout_seconds`, `idle_timeout_seconds`) are defined in `models.yaml`. An API key is given by `api_key_from` in `models.yaml` (`env:NAME` such as `env:OLLAMA_API_KEY`, `env:OPENROUTER_API_KEY`, `env:OPENAI_API_KEY`, or `file:/path`); a missing credential disables that provider and never stops startup (the router's existing behaviour).
5. The per-purpose `think` is a model option in `models.yaml` (as in phraseforge); the purpose keeps `num_ctx`, `timeout_seconds` and `prompt`.

Task purposes through the router
6. `chat` sends its message history (system prompt, earlier turns, the new user message) as `router.Request.Messages`; `generate_title`, `generate_summary` and `translate` send a system prompt and one user message. All four go through `shared/router`: the highest-priority available model with all the tags is tried first, a failure falls back to the next, the circuit breaker holds a failing model or an unreachable provider out for its cooldown, and a cancelled context stops the chain at once.
7. A call that fails on every model returns an error listing each model and why; the existing retry behaviour of the queue (`knowledge/internal/queue`) still applies to it.
8. `knowledge/internal/chat`, `generate` and `translate` no longer import `shared/llm` for these calls.

`models.yaml` in the cluster
9. ConfigMap `knowledge-models` is created by the Taskfile from `knowledge/models.dev.yaml`, validated first with the assistant's `models validate` (`cd assistant && go run . models validate <file>`); when `.k3d/llm/knowledge-models.yaml` exists it is used instead. The Deployment and the migrate Job mount `knowledge-config` and `knowledge-models` into `/etc/knowledge` as a projected volume, as phraseforge does.
10. `deploy-knowledge` applies `knowledge-config` and `knowledge-models` before the migrate Job and before the Deployment; the migrate Job's pod spec is checked (it mounts the same config, because `migrate` loads the config, which now includes `models.yaml`). `delete-knowledge` removes `knowledge-models`.
11. `knowledge/k8s/deployment.yaml` gets the optional Secret env vars and the optional `knowledge-vertex` volume the other apps have (`knowledge-llm-keys` with optional `OLLAMA_API_KEY`, `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`; volume `knowledge-vertex`, optional, mounted at `/etc/knowledge-vertex`), so the pod starts without them.

Embeddings
12. `shared/router` gains an embeddings API (a request with one input text and the embedding space; a response with the vector and token count), reusing selection, breaker, attempt observer and logging. It is tested only against fake HTTP servers and a scripted provider.
13. Providers in scope: ollama (`POST {base_url}/api/embed`, verified 2026-10-22 against the local Ollama: the reply has `embeddings`, an array of vectors) and openai-compatible (`POST {base_url}/embeddings`, as `knowledge/internal/embeddings` calls it today; unverified against a real server, fake server only). Vertex embeddings are out of scope (see Out of Scope). The loader rejects an embedding model on a provider of a type without an embeddings implementation (anthropic, vertex, demo), naming the model and the provider.
14. A `models.yaml` model entry may have `embedding_space` (a name matching `^[a-z][a-z0-9-]*$`) and `dimension` (integer, at least 1); both or neither. A model with `embedding_space` is an embedding model: it is never a candidate for a chat purpose, and a chat model is never a candidate for embeddings. The schema in `shared/modelcfg` and its lint accept and check the two keys, rejecting one without the other.
15. Knowledge's `config.yaml` names the space and dimension it needs in `embeddings.embedding_space` and `embeddings.dimension`. Startup fails when no model has that space, or when a model of that space declares a different dimension (naming the model, both dimensions). Embeddings use no `model_tags`: the space is the only selector.
16. The router selects only embedding models of the requested space, highest priority first. A model of another space is never tried, even when every model of the requested space has failed; the error then lists the models tried and says no other space is used.
17. A reply whose vector length differs from the configured dimension is a failed attempt (outcome `error`, never returned, never stored); a reply with no vector is a failed attempt.
18. The embedder knowledge uses (the `embeddings.Embedder` interface: `Embed`, `Dimension`, `Model`) is implemented over the router and has no dependency on `internal/qdrant` or any vector-store package; `Model()` returns the space name, which `qdrant` stores as the item's `EmbeddingModel`. Embedding an ingested chunk and embedding a search query are the same call. Existing items stay valid when the space name is chosen equal to the model name stored today (`bge-m3`, `knowledge/k8s/configmap.yaml`).
19. `fake` embeddings (`embeddings.provider: fake` today) remain available to tests and local runs without any provider.

Records, metrics, admin
20. Table `llm_calls` (created by the migrate step) has one row per attempt, embeddings included, with the columns of phraseforge's `llm_calls` (`id`, `job_id` nullable without foreign key, `kind`, `model_id`, `provider_id`, `model_name`, `tags`, `input_tokens`, `output_tokens`, `cost_usd`, `started_at`, `duration_ms`, `outcome` in ok|error|timeout|rate_limited|canceled, `error`, `http_status`, `request_id`) except `source_language` and `target_language`, which knowledge's calls do not have. `kind` is one of `chat`, `generate_title`, `generate_summary`, `translate`, `embed`. No prompt, reply, text or vector is stored. The recorder is a `router.Observer`; a failed insert is logged and counted and never fails the call.
21. Rows older than `llm_calls.retention_days` (default 30; 0 keeps forever; negative or above `retention.MaxDays` rejected at config load) are purged by `shared/retention` in batches, every 6 hours and shortly after start, as in phraseforge.
22. Metrics with prefix `knowledge_llm_`, in the names of phraseforge's: `_calls_total{provider,model,outcome}`, `_tokens_total{provider,model,direction}`, `_cost_usd_total{provider,model}`, `_call_duration_seconds{provider,model}`, gauge `_model_available{model}`, `_record_errors_total`, `_calls_purged_total`. Labels are configured ids only.
23. `GET /metrics` is served on the main listener outside the login, like phraseforge's `SetMetricsHandler`; it returns 200 without a cookie.
24. The router writes one slog line per attempt through the existing router logging options; no prompt, reply, text, vector, header value or API key appears in any log line.
25. Admin pages for usage, models and attempts use the shared UI components (`dp-usage-table`, `dp-model-table`, `dp-attempt-table` from `shared/ui`), with endpoints for models, attempts and per-model usage as phraseforge's `/api/v1/admin/models`, `/llm-calls` and `/llm-aggregates` (their responses contain no URL, key, variable name or upstream model name). Knowledge has no admin role today (see Approach, open question 1); until the user decides, the pages are visible to any signed-in user. The pages are checked in a real browser at 1280 px and 1024 px with screenshots (`ui-verification` skill), including long model ids and long error texts.

Tooling and tests
26. The `llm-*` tasks cover knowledge: `llm-enable` writes `.k3d/llm/knowledge-models.yaml` (the committed dev file plus the enabled sources, priorities LAN 100, OpenRouter 90, Vertex 80, local 10, tags `default` and `chat`); an embedding entry for a LAN Ollama is added only when that machine lists the embedding model; `llm-enable` and `llm-disable` apply `knowledge-models`, create the optional `OPENROUTER_API_KEY` Secret entry and the `knowledge-vertex` Secret like for the other apps, restart `knowledge`, and the single never-overwrite rule (an existing Secret or key `llm-enable` did not create is refused) applies to any new Secret; `llm-status` is unchanged in behaviour; `task test-llm-scripts` covers knowledge.
27. All tests are LLM-free: providers against fake HTTP servers, the router against a scripted provider with an injected clock, knowledge's purposes against a scripted provider. `go vet` and `go test` pass in `shared` and `knowledge` with no model reachable. At the end, at most 1 to 3 real calls through the dev laptop's Ollama (one chat or title call, one embedding call with `bge-m3`), after a precheck, under strict timeouts, with the model unloaded afterwards.
28. Every step is deployed on the dev cluster with `task deploy-knowledge` and the app works (login, search, chat, ingest) before the next step starts.

Documentation
29. `knowledge/README.md` (Configuration, Ollama notes, OpenAI/OpenRouter-compatible embeddings, Deploy) and `knowledge/CHANGELOG.md` describe the snake_case keys, `models.yaml`, the embedding-space rule, `llm_calls`, `/metrics` and the admin pages, and state the breaking change: the new image and the production Helm chart values must change together, and the chart (outside this repo) needs `knowledge-config` and a `models.yaml` rendered from its values. ## Approach

Memory consulted: knowledge, router, embed|bge-m3|qdrant, camelCase|snake — 33, 5, 11, 1 hits; relevant: knowledge config from a mounted config.yaml with PG credentials and API keys as env (2026-09-21T18:39:17Z), deploy-knowledge applies the migrate Job before the Deployment so ConfigMaps must exist first (2026-09-21T18:39:18Z), snake_case in knowledge row structs (2026-09-21T20:21:19Z), shared/router error texts never name a dev task (2026-10-22T17:18:11Z), the router migration needs a read-only row count before migrating a real database (2026-10-20T20:28:39Z; for knowledge no table stores provider or model, to be confirmed).

Reuse the phraseforge design: `shared/modelcfg` and `shared/router` as they are, a thin knowledge adapter that turns a purpose into a `router.Request` (tags, `Messages`, `NumCtx`, timeout), a recorder implementing `router.Observer`, and `shared/retention` for the purge. New in `shared`: the embeddings API (router, the ollama and openai providers) and the `embedding_space` and `dimension` model keys (modelcfg schema and lint). In knowledge, `internal/embeddings.Embedder` stays the interface `qdrant` takes (`qdrant.New(base, collection, emb, minScore)`), but its implementation calls the router; nothing in `internal/embeddings` imports `internal/qdrant`, so a different vector store can use it unchanged.

Ordered plan; every step ends deployed on the dev cluster and runnable, in the order that gives value early:
1. Config, `models.yaml` and snake_case keys, with chat, title, summary and translate through the router, Ollama only (AC 1 to 11, 6 to 8). Embeddings still use the existing client. Because the `providers` block is gone from `config.yaml` in this step, the `embeddings` block temporarily keeps `provider`, `model` and `dimension` and gains a transitional snake_case `base_url` (the API key stays in `OLLAMA_API_KEY` or `OPENAI_API_KEY`/`OPENROUTER_API_KEY`); step 3 removes all of these in favour of AC 15. This transitional key is my proposal, not a user decision.
2. The `llm-*` tasks cover knowledge for these purposes (AC 26, without the embedding entry).
3. Embeddings API in `shared/router` with fake-server tests (3a), then knowledge embeddings through it with the space rule and the loader checks (3b) (AC 12 to 19). Needs the user's approval of the rule first. Existing items need no re-embedding when the space name equals the stored model name; a different space or dimension needs a new collection (qdrant already refuses a collection with another vector size).
4. `llm_calls` table, recorder, retention, metrics and `/metrics` (AC 20 to 24); adds the Prometheus client to knowledge.
5. Admin pages (AC 25), browser-verified.
6. Documentation, changelogs, `llm-*` embedding entry, final 1 to 3 real calls (AC 26, 27, 29).

Cost: about 7 reviewable steps (the six above, with step 3 in two parts), comparable to the phraseforge router feature; the shared router and modelcfg work already exists, so the new work is the knowledge adapter, the embeddings API, the observability stack and the key migration. I do not give a time estimate.

Risks:
- Breaking config change: an existing deployment, including the production Helm chart (outside this repo), fails at startup with a message naming the old key until `config.yaml` and `models.yaml` are both updated; the new image and the chart values must deploy together.
- Index corruption if the embedding-space rule is wrong or a `models.yaml` entry declares the wrong space or dimension: the dimension check catches only a length mismatch, not a different vector space of equal length.
- Prometheus and a metrics endpoint are new to knowledge; `/metrics` is outside the login and its exposure through the ingress is a deployment decision, as for phraseforge.
- `llm_calls` insert is synchronous in phraseforge (up to 5 s per attempt with the database down); knowledge inherits that trade-off unless the user decides otherwise.

Open questions for the user:
1. Admin access: knowledge has a `users` table with no role column, so "admin pages" have no admin. Proposal: any signed-in user until roles exist.
2. `llm_calls.job_id`: knowledge has two tables, `jobs` (ingest) and `operations` (queue); which id to record, and whether it is available in the handler context, is to be confirmed in step 4.
3. Embedding requests carry one text per call, as today; batching is not planned.

- A pgvector store, or dropping Qdrant (only keep the door open: the embedder does not depend on Qdrant).
- Production Helm chart changes (documented only).
