## Problem / Motivation

Three apps have three hand-written Web Component sets that duplicate each other: `as-*` (14 components) in assistant, `kb-*` (8) in knowledge and `pf-*` (11) in phraseforge, each with its own button, card, dialog, field, status bar and pager or nav. Phraseforge has the layout the user wants everywhere: a top bar, a sidebar that collapses, a theme toggle and a status-bar footer. The assistant has a narrow fixed-width page with a permanent sidebar and a chat that is not prominent.

The assistant is going to become an orchestrator that calls subagents and workflows and renders a2ui components in the chat, with a large catalog of custom components later. That needs one shared component base before the catalog grows, not three copies.

This feature is the first step only: review the GUIs, extract the common patterns into one shared library built with Lit, build the phraseforge-style shell as a shared component, and convert all GUIs to use them. The a2ui catalog and the orchestrator are later work.

Decisions confirmed by the user (2026-10-21): a shared Go module with `go:embed`, serving the library to each app; components written in TypeScript with Lit, bundled by esbuild with code splitting (revised the same day from "vendored Lit, no build step", after the user asked for TypeScript); Shadow DOM with CSS custom properties for theming; phraseforge is the reference design and is converted first; the `dp-` tag prefix; old per-app components are deleted once nothing uses them; dictionary has no GUI and is not touched. All GUIs get phraseforge's layout eventually.

Assumptions: Lit 3.3.3 is the version to use (`npm view lit version` on 2026-10-21). Checked on 2026-10-21: a Lit element with Shadow DOM, a reactive property, a slot and a composed event works under jsdom 30.1.3, and Node v26.8.2 runs `.ts` files directly. Not yet checked: Lit under jsdom when the test imports TypeScript source, and the speed gain of splitting over plain modules (to be measured, not assumed).

## Approach

Memory consulted: component|frontend|lit — 3 relevant entries (the light-DOM `kb-*` pattern and its jsdom test setup, the `node --test` discovery limit, and the `.tab.active` focus gotcha)

Chosen approach: one new Go package `shared/ui` with `go:embed`, served by a small handler that every app mounts at `/ui/`. The three apps already depend on `shared` through a `replace` directive. Components are TypeScript with Lit, using `static properties` rather than decorators, and esbuild bundles them into `dist/` with code splitting: a small core for the shell and the common components, and separate chunks for catalog components that a page loads on demand, so an app never downloads components it does not use. `dist/` is built, not committed. Each app's Dockerfile gets one Node build stage for `shared/ui`, and `task build-ui` does the same locally. Shadow DOM encapsulates each component; theme and spacing come in through CSS custom properties from `tokens.css`, so apps keep one palette. Tags use the `dp-` prefix.

Alternatives considered: copying files into each app with a Taskfile task (creates duplicate files in git); vendoring one Lit file with plain JavaScript and no build (chosen first, then replaced by the user in favor of types and splitting); plain JavaScript with JSDoc types and `tsc --noEmit` (no build, but no splitting and more verbose types); light DOM (loses slots and style isolation, which a large a2ui catalog needs).

Ordered plan, one slice at a time, with a go-ahead between slices:
1. S0 (done, then revised): `tech-stack.md` version 21 and this spec version 2 for the TypeScript build.
2. S1: `shared/ui` with package.json and lockfile, the esbuild task, the Go handler and `dist` placeholder, `tokens.css`, `dp-button`, tests and type check, the Dockerfile Node stage, mount in phraseforge, one page converted, screenshots.
3. S2: extract the six components one at a time, converting phraseforge as each lands.
4. S3: `dp-shell`, phraseforge on it.
5. S4: assistant on it, with the fluid layout and the hideable sidebar.
6. S5: knowledge on it.

Risks: a gitignored `dist/` means a clean checkout needs `task build-ui` (or the tracked placeholder) before Go builds, and the Node stage needs `npm ci` to work behind the corporate CA, both checked in S1; TypeScript tests depend on Node's type stripping, which allows only erasable syntax (no enums, parameter properties or decorators); Shadow DOM stops page-level CSS from reaching inside a component, so existing page styles for converted elements must move into the component or the tokens; phraseforge has per-script CSS (`arab.css`, `hebr.css` and others) that must still apply to text inside components, to be checked with the right-to-left and CJK lists in S2. Phraseforge's templates and `shell.js` are the reference, and its behavior must not change.

Testing strategy: Node and jsdom per component, run in under a few seconds; Playwright screenshots on dev per slice; no Ollama.

S2 step 2, `dp-field` (2026-10-21):
