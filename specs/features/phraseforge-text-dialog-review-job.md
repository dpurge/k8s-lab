## Problem / Motivation

Roadmap item `phraseforge-text-dialog-review-job`: the transcription and translations of a text or dialog are generated by a small local model and can be unfaithful or unnatural. As for the vocabulary review (`phraseforge-vocabulary-review-job`, whose decisions are reused: proposals stored and applied by a person, one job per resource, a model chosen in the settings), a more capable model reviews them. Decisions taken with the user while building: the transcription and the translations are reviewed separately (own button, job, call and stored proposals), each with its own model configuration and its own prompt (purposes `reviewTranscription` and `reviewTranslation`); dev and prod both use gemma4:12b for the review purposes for now (gemma4:26b needs 16-19 GB and does not fit the prod Ollama); a bigger model is set per purpose in jdp-helm jdp-frontend values.yaml (and listed in jdp-backend ollama.models). Taken by default for speed (the user asked to work fast, so this spec was written with the work, not approved before it): one call per part; a text over 12000 characters (source plus reviewed part) is refused with a clear error instead of being chunked; a proposal is the whole corrected text of a locale or of the transcription; the review is made against the text and the vocabulary list generated from it as context.

## Acceptance Criteria

- [x] Purposes `review_transcription` and `review_translation` (config keys `reviewTranscription`, `reviewTranslation`; config.yaml, Helm values, admin LLM list, `ValidKinds`, DB kind constraint, placeholders) each with its own prompt (prompt-eval `review-transcription.txt`, `review-translation.txt`, synced), reply schema (`ReviewTranscriptionSchema`, `ReviewTranslationSchema`, checked by `check-sync`) and prompt-eval suite; a blank provider or model falls back to `reviewVocabulary`'s, then `vocabularyItem`'s.
- [x] Job kind `review_text`, payload `{resource_type: text|dialog, resource_id, part: transcription|translation}`; it reads the resource, its translations and the attached vocabulary list (up to 100 phrases with translations), sends only the reviewed part, stores findings (status open) in `resource_reviews` (one row per resource and part, replaced by the next review), ends as skipped when the resource is gone or its source text was edited meanwhile.
- [x] A transcription finding only when the resource has a transcription and its language a transcription snippet; translation findings per locale the resource has; unknown locales, malformed entries and checks without a fix or reason ignored; an invalid reply is corrected within the attempt budget.
- [x] Endpoints (edit right on the language): `POST /api/v1/{texts|dialogs}/{id}/review/{part}` (no second job while one waits), `GET` (`{pending, review}`), `POST .../apply` and `.../dismiss` with `{indexes}`; 409 when the source text changed, 404, 400, 403 as for the vocabulary review.
- [x] Apply overwrites the transcription or one translation only while the source text is the reviewed one and the value is the reviewed one (an edited value is a conflict and stays open); remarks are not applicable; each part is applied on its own.
- [x] GUI on the text and dialog view pages (editors only): Review transcription and Review translation buttons, a status line with a link per part ("N open", "reviewed", "outdated", "reviewing…" polled while a job waits) and a proposals dialog with Apply and Dismiss per proposal and for all, Review again; strings in en and pl.
- [x] Docs (README, CHANGELOG), Helm values for prod.

## Approach

Reused the vocabulary review's pattern with a new store (`internal/resreview`, polymorphic over texts and dialogs, no foreign key like `resource_translation`) because a review overwrites only a transcription or one translation, guarded by a hash of the source text computed in SQL; one shared script (`static/js/text-review.js`) serves both view pages. The single `review_text` purpose first built was split in two on the user's request (separate model configuration and prompts).

## Out of Scope

Chunking texts longer than 12000 characters; reviewing a text's title or body; per-line suggestions; the vocabulary review (separate feature).
