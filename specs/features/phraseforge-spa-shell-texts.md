## Problem / Motivation

First and foundational item of phraseforge's SPA migration (`specs/artifacts/phraseforge/roadmap.md`). Today, Texts is 4 separate server-rendered templates (`list.html`, `new.html`, `edit.html`, `view.html`) with zero JSON API — every action is a full page load. This feature proves the whole SPA pattern (JSON API, client rendering, IME re-wiring, in-page navigation) on Texts alone before repeating it for Dialogs/Vocabulary/Models/Admin/Profile in later roadmap items.

Per the user's explicit decisions this session:
1. **No deep-linking** — matching knowledge exactly (verified: knowledge has zero `pushState`/`popstate`/URL-based routing, pure in-page state). `/texts/{id}`-style bookmarks stop working; everything happens at `/`.
2. **Keep i18n** — the current locale's translated UI strings are embedded into the SPA shell's initial load (knowledge itself has no i18n at all — single locale — so this is a deliberate, evidence-based departure from "just like knowledge," made because phraseforge already serves English/Polish and dropping that would be a real regression for Polish-speaking users).
3. **Transitional nav** — Dialogs/Vocabulary/Models/Admin/Profile stay plain `<a href>` links to their existing server-rendered pages until their own roadmap items land. Only the "Texts" nav link becomes JS-intercepted.

**Key finding that de-risks and shapes this feature**: since Dialogs/Vocabulary/Models/Admin/Profile all still need `layout.html` to render during this transition, `layout.html` itself cannot be replaced by a standalone static shell yet — doing so would require duplicating its header/`pf-nav`/theme/`pf-dialog` chrome into a second file, a real duplication risk for no benefit. Instead, "the SPA shell" for this feature is a **new, single, minimal template** (`texts-app.html`) that extends `layout.html` exactly like every other page — its `{{block "content"}}` is just an empty container plus a bootstrap JSON blob and a script include. This consolidates 4 templates into 1 (directly addressing "templates directory is crowded") without touching the shared chrome any other page still depends on.

**Second key finding**: `view.html`'s `RenderedBody`/`RenderedTranscription`/`RenderedTranslation` are already `template.HTML`-typed (Go's trusted-HTML marker, confirmed via `handleView`) — they come from `texts.RenderHTML(...)`, phraseforge's own controlled markdown renderer, not raw user input. The new JSON API can return these same HTML strings, and the client can insert them via `innerHTML` at the exact same trust level as today. **No new sanitization library, no `tech-stack.md` change** — this isn't knowledge's situation (arbitrary chat-rendered markdown), it's the same server-controlled content phraseforge already trusts.

**Third finding, caught before implementation started (self-correction against the original roadmap line)**: the roadmap item named `pf-status-bar` as part of the shell, but the first draft of this spec omitted it. That's not cosmetic — once Texts create/update/delete become `fetch()`-based, the *existing* flash-message toast (`.Message`/`.MessageType`, set server-side and shown once on the next full-page GET after a POST-redirect) never fires again, since there is no more full-page reload to carry it. Without a replacement, save/delete/validation-error feedback on the new Texts flows would silently disappear. Confirmed with the user: build `pf-status-bar` (mirroring `kb-status-bar`'s exact API — a job-status span and a message span, `setJobStatus(text)`/`setMessage(text, isError)`) as part of this feature, added once to `layout.html` (global, like `pf-dialog` — present but unused on pages not yet part of the SPA). The **existing** flash-message toast is *not* removed — Dialogs/Vocabulary/Models/Admin/Profile/login/signup still rely on it until their own roadmap items convert them; both mechanisms coexist during the transition, same pattern as the transitional nav-links decision.

- New template `phraseforge/internal/server/templates/texts-app.html`: extends `layout.html`, `Nav: "texts"` (static — the page's active-nav-link never changes server-side anymore), content is `<div id="texts-app"></div>` + `<script>window.__PF_TEXTS_BOOTSTRAP__ = {{.BootstrapJSON}};</script>` (a `template.JS`-typed field) + `<script src="/static/js/texts-app.js">`.

- New JSON API, `/api/v1/texts` (new `r.Route("/api/v1", ...)` nested inside the existing `requireAuth` group — phraseforge's first such group): `GET /api/v1/texts?language=` (list), `POST /api/v1/texts` (create), `GET /api/v1/texts/{id}` (one, including pre-rendered HTML fields), `PUT /api/v1/texts/{id}` (update), `DELETE /api/v1/texts/{id}` (delete). Each preserves the **exact same business logic** as today's `handleList`/`handleCreate`/`handleView`/`handleUpdate`/`handleDelete` (the same `s.roles.CanView`/`CanEdit` checks, the same `s.tags`/`s.translations` calls, the same `texts.RenderHTML`) — only the transport changes (JSON in/out instead of form values in/HTML out), including the exact same authorization semantics (`CanView` denied → 404, matching today's "don't reveal existence" pattern; `CanEdit` denied → 403 on create, 404 on update/delete, matching today exactly).
- `phraseforge/internal/server/static/js/texts-app.js` renders, entirely client-side against the new API: the list (via `pf-card` per item, mirroring `phraseforge-pf-list-card-components`'s markup shape), the New/Edit form (via `pf-field`/`pf-button`, reusing the exact `pfApplyImeConfig`/`pfWireIme`/`pfApplyScriptStyle`/`pfSwitchTab` functions already in `editor.js` **unchanged** — called explicitly after each render instead of relying on `DOMContentLoaded`, since the form's DOM now appears/disappears dynamically rather than via page load), the view (inserting the API's pre-rendered HTML fields via `innerHTML`, same trust level as today), and delete (`pf-dialog.confirm()` used in `kb-dialog`'s **original** async fetch-await pattern — `if (await confirmDialog.confirm(...)) { await fetch(DELETE...) }` — simpler than the form-submit-interception mechanism built for `phraseforge-pf-dialog-admin-components`, since there is no real form submission left to intercept once this is a fetch-based SPA flow).
- `phraseforgeCopyMarkdown`/`phraseforgeCopyActiveMarkdown`/`phraseforgeGenerate` (in `layout.html`'s shared script) are **not modified** — they already operate on elements by ID (`#field-source` etc.), agnostic of how those elements got into the DOM, so they keep working unchanged once `texts-app.js` renders the same IDs.
- The sidebar's "Texts" `<a href="/">` link gets one small addition in `texts-app.js`: a click listener that `preventDefault()`s and calls the in-page router instead of navigating — **`pf-nav` itself is not changed at all** (it was already designed, in `phraseforge-pf-components-foundation`, to just wrap real links with no interception — this feature validates that design was right, rather than requiring a retrofit). Dialogs/Vocabulary/Models/Admin/Profile's nav links are untouched, real navigation, per the approved transitional-nav decision.
- `GET /` (inside the `requireAuth` group) now renders `texts-app.html` (replacing `handleList`). Removed entirely: `GET /texts/new`, `GET /texts/{id}`, `GET /texts/{id}/edit`, `POST /texts`, `POST /texts/{id}/edit`, `POST /texts/{id}/delete`, and their handlers (`handleNewForm`, `handleView`, `handleEditForm`, `handleCreate`, `handleUpdate`, `handleDelete` as HTML handlers — their business logic moves into the new JSON handlers, not duplicated). Removed templates: `list.html`, `new.html`, `edit.html`, `view.html`.
- No change to `Dialogs`/`Vocabulary`/`Models`/`Admin`/`Profile`'s templates, routes, or handlers. No change to `login.html`/`signup.html`. No change to any `pf-*` component's own files.
- `go build`/`vet`/`gofmt -l .` clean. `task test-phraseforge-frontend` passes (existing 22 tests) plus new jsdom tests for `texts-app.js`'s pure logic (rendering functions, router dispatch) where feasible without a full DOM-diffing framework.
- Live end-to-end validation: deploy; as the seeded `admin` account, exercise the full Texts lifecycle (list, create, view with a language/script requiring the IME/transcription tab, edit, delete) entirely through the new SPA — no full page reload during any of it (confirmed by checking `window.location` never changes path) — plus confirm the four other nav links still do real page loads to their existing pages, unaffected.

## Approach

**This is the largest single feature in this project's `pf-*`/layout series — by design, broken into many small, independently-validated steps within B2, not one large silent pass:**

1. **Build the JSON API first**, alongside the still-live old HTML routes (temporary overlap is fine *within* this feature's own implementation — both exist briefly while the client is built against the new one; the old routes/templates are removed only once the new flow is fully validated, per the last step below, honoring "remove as you go" at the *feature* level as agreed).
2. **Build `texts-app.html` + `texts-app.js`'s list view only** (read-only), wired to `GET /api/v1/texts`, using `pf-card`. Validate against real data before continuing.
3. **Add the New/Create flow** (form via `pf-field`/`pf-button`, IME re-wiring, `POST`). Validate.
4. **Add the View flow** (pre-rendered HTML insertion, Copy button reuse, transcription/translation tabs). Validate.
5. **Add the Edit flow** (reuses the New form's rendering code, prefilled, `PUT`). Validate.
6. **Add the Delete flow** (`pf-dialog.confirm()` + `DELETE`, fetch-based). Validate.
7. **Wire the Texts nav link's client-side interception; switch `GET /` to the new shell; remove the old routes, handlers, and templates.** This is the actual cutover — everything before this step could still fall back to the old templates if something didn't work; after this step, Texts has no server-rendered fallback.
8. **Full live validation** across every flow, on the real deployed app, before calling this done.

**Key decisions** (see Problem/Motivation for the two most consequential ones — the single-template-shell-reusing-`layout.html` design, and the `template.HTML`/no-new-sanitization-library finding):

- Bootstrap data (nav flags, languages, scripts, tags, i18n strings) is embedded once at shell-load, not fetched via a separate API call — it's the exact same data `handleList` already gathers server-side today; JSON-encoding it once is strictly simpler than adding a `/api/v1/me`-style endpoint for data that doesn't change within a session.
- i18n strings ship as a flat `{key: translatedString}` object in the bootstrap payload, gathered via the same `i18n.T(u.Locale, key)` calls `layout.html`'s templates already make — just collected into JSON instead of interpolated into HTML.
- Delete goes back to `kb-dialog`'s original async-await pattern (not the form-`data-confirm` mechanism built one feature ago) — that mechanism existed specifically to bridge a *real form submission's* synchronous `onsubmit`; once delete is a `fetch()` call with no form involved, the bridge is unnecessary complexity to carry forward.

**Risks & testing strategy:**

- Highest risk: silently regressing one of the many authorization/business rules currently spread across 5 HTML handlers (per-language `CanView`/`CanEdit`, tag/translation side effects) while rewriting them as JSON handlers. Mitigated by porting each handler's logic as a near-literal transcription (same calls, same order, same error handling) rather than a rewrite, and by live-validating every authorization edge already known from this session (e.g., the no-grants-yet signup user got a real 403 earlier in this project — that exact check must still 403 the same way from the JSON endpoint).
- Second risk: `editor.js`'s IME wiring assumes call-once-per-page-load; re-rendering the New/Edit form multiple times in one SPA session (list → new → list → edit → ...) must not accumulate duplicate event listeners. Mitigated by always fully replacing the form container's contents on each render (fresh DOM nodes each time, matching knowledge's own `render*()` pattern) rather than patching in place — old nodes and their listeners are garbage-collected once removed, no duplicate-listener risk by construction.
- No browser automation available this session (consistent with every prior frontend feature here) — "no full page reload happened" is checkable via `curl`/session-based scripting (confirm no new `Set-Cookie`/redirect chain, confirm the API calls happened) but the *visual* SPA experience needs the user's own spot-check after deploy.

## Implementation Notes

**Step 1 — JSON API.** Added `writeJSON`/`writeErr` helpers mirroring knowledge's own `{"error":{"code","message"}}` shape exactly, and `apiListTexts`/`apiCreateText`/`apiGetText`/`apiUpdateText`/`apiDeleteText` under a new `r.Route("/api/v1", ...)` group — each a near-literal transcription of the old HTML handler's logic (same `s.roles.CanView`/`CanEdit` calls in the same order, same `s.tags`/`s.translations` side effects, same `texts.RenderHTML` calls), just JSON in/out instead of form values in/HTML out. Confirmed `RenderedBody` etc. are already `template.HTML`-typed (checked `handleView`'s source directly) — the JSON API returns them as plain strings at the exact same trust level the server already used, no new sanitization needed.

**Step 2 — the shell.** Built `pf-status-bar` (mirroring `kb-status-bar` exactly — job-status span, message span, `setJobStatus`/`setMessage`) and added it globally to `layout.html` inside a new `<footer>`, extending `body`'s grid from 2 rows (`auto 1fr`, from `phraseforge-scroll-independent`) to 3 (`auto 1fr auto`). The existing flash-message toast is untouched — still load-bearing for every page not yet part of the SPA. Built `texts-app.html` (extends `layout.html`, empty `#texts-app` container + bootstrap JSON + script include) and `handleTextsApp` (gathers the same data `handleList`/`handleNewForm` already gathered, JSON-encodes it once — including a flat `{key: translatedString}` i18n dict built from the exact 26 keys grepped out of the four templates before removing them). `GET /` switched to `handleTextsApp`.

**Steps 3–6 — `texts-app.js`.** Built the list (via `pf-card`), New/Edit (shared `showForm(existing)` function — `pf-field`/`pf-button`, calling `pfInitEditor()` explicitly after each render since `editor.js`'s own `DOMContentLoaded` call is a no-op the first time `#texts-app` is still empty), View (inserting `renderedBody`/etc. via the same untrusted-vs-trusted boundary the server always used), and Delete (`pf-dialog.confirm()` used in its original async `await`-based form — no `data-confirm`/`form.submit()` bridge needed, since there's no real `<form>` submission left to intercept once this is `fetch()`-based).

**Step 7 — cutover.** Wired the sidebar's "Texts" `<a href="/">` click to call the in-page router (pf-nav itself untouched — validates its original real-links-only design). Removed `handleList`, `handleNewForm`, `handleCreate`, `handleView`, `handleEditForm`, `handleUpdate`, `handleDelete` and the `GET /texts/new`, `GET /texts/{id}`, `GET /texts/{id}/edit`, `POST /texts`, `POST /texts/{id}/edit`, `POST /texts/{id}/delete` routes; deleted `list.html`/`new.html`/`edit.html`/`view.html`. `formOptions`/`filterByID` kept (still used by the new API handlers and by dialogs' own list handler respectively).

**A genuine validation-methodology gap found and closed during this feature**: every prior frontend feature's `curl`-based validation exercised the *server* side of a flow; this feature's actual risk (does the client JS render/submit/confirm correctly against real API responses) is invisible to `curl` — posting straight to a JSON endpoint always "succeeds" regardless of whether the client would have gotten there correctly. Closed by extending the project's established "execute the real deployed script in Node+jsdom" technique one step further: instead of extracting just one script block, the validation script built one complete jsdom document with every real script (`ime.js`, `editor.js`, the shared layout script, `pf-*` components, `texts-app.js`) injected as literal inline `<script>` tags in the real page's own load order, with `fetch` shimmed to real `curl` calls against the live backend. This actually exercises the full New→View→Edit→Delete cycle through real code and real data. **One harness bug found and fixed along the way** (not an app bug): an initial version loaded `editor.js`/`texts-app.js` via Node's `import()`, which gives each file its own ES module scope — `texts-app.js`'s bare reference to `pfInitEditor` (a top-level `function` in `editor.js`) came back `undefined`, because ES modules never attach top-level declarations to a shared global object the way classic `<script>` tags do in a real browser. Fixed by injecting all of them as real inline `<script>` tags in one jsdom document instead, restoring the shared-global-scope behavior real browsers actually have.

**Final file list**: modified `phraseforge/internal/server/server.go`, `phraseforge/internal/server/templates/layout.html`; new `phraseforge/internal/server/templates/texts-app.html`, `phraseforge/internal/server/static/js/texts-app.js`, `phraseforge/internal/server/static/components/pf-status-bar/{component.js,component.css,component.test.js}`; removed `phraseforge/internal/server/templates/{list,new,edit,view}.html`.

**Self-review** (code-review + security-review): every authorization check in the new JSON handlers matches its HTML predecessor's exact call and ordering — re-verified by diffing against the removed handlers before deleting them. No new attack surface: `renderedBody`/etc. carry the same trust level as before (Go's own `template.HTML` marker, not client-supplied); `apiTextRequest`'s fields are decoded via `encoding/json` into typed struct fields (no arbitrary key injection risk); the i18n dict embedded in the bootstrap script is `json.Marshal`-escaped, not string-concatenated.

**Live end-to-end validation** (deployed via `task deploy-phraseforge` at every step; no template-parse panic at any point):
- Full JSON API lifecycle (list/create/get/update/delete) exercised directly via `curl` as the seeded `admin` account — correct data at every step, correct `404`/error shape for a nonexistent id, correct `302` redirect for an unauthenticated request.
- Full client-rendered lifecycle (New → View → Edit → Delete, including the real `pf-dialog` confirm) exercised via the jsdom-based technique described above, against the real deployed code and real backend — every step confirmed correct: form submission created the text, view rendered the real HTML body, edit correctly prefilled the existing title and saved the update, delete showed the real confirm message and, once confirmed, actually removed the text (list returned to 0 cards, confirmed via a follow-up direct API call too).
- Post-cutover: confirmed `GET /texts/new`, `GET /texts/{id}`, `GET /texts/{id}/edit` are now `404`; `GET /` still serves the shell; `/dialogs`, `/vocabulary`, `/models`, `/admin`, `/profile` are all still `200`, unaffected; one final create/get/delete cycle via the API confirmed the whole thing still works after the dead-code removal.
- **Cleanup**: every test text created during validation was deleted via the real API; confirmed gone. No residual test data.

**Known gap (consistent with every prior frontend feature in this project)**: no real browser was used — the jsdom-based technique proves the real code executes correctly against real data, but pixel-level appearance (the status bar's footer placement, the SPA transitions feeling instant) needs the user's own visual spot-check.

**Real regression found by the user after this feature's initial "done" validation — not caught by any automated or jsdom-based check above.** The user reported the Texts workspace rendering completely empty in a real browser (no title, no button, nothing). Root cause: `<script src="/static/js/texts-app.js">` sits inside `<main class="content">`, which in `layout.html`'s markup comes *before* `<footer><pf-status-bar id="statusBar">`. A plain (non-`defer`) `<script>` tag executes the instant the browser's parser reaches it — so `document.getElementById("statusBar")` ran before the footer had even been parsed, returned `null`, and `showList()`'s first line (`statusBar.setMessage("")`) threw immediately, aborting before ever reaching the `root.innerHTML = ...` line. Confirmed exactly by the user's own browser console: `TypeError: Cannot read properties of null (reading 'setMessage') at showList (texts-app.js:54:15)`.

**Why every validation in this feature missed it**: every jsdom-based check in this feature (and the wiring-logic test from the previous feature) built its own synthetic HTML with every element — including `#statusBar` — already present *before* any script ran. That construction accidentally guaranteed the exact ordering a real document does not: `layout.html`'s actual markup puts the footer *after* the main content area, and nothing before this bug forced a validation to load the real page's real script-tag position relative to the elements it looks up.

**Fix**: added `defer` to `texts-app.html`'s one script tag — `defer` scripts execute only after the entire document has finished parsing (still before `DOMContentLoaded`), regardless of where the tag itself sits in the markup. Verified the fix by rebuilding the validation to respect real script-tag order and `defer` semantics properly this time (execute every non-deferred script in document order first, exactly as a browser does, then every deferred script after) against the real deployed page — `#texts-app` now renders the title and the New button correctly.

**New `[gotcha]`/`[convention]` recorded in `specs/memory.md`** (see Documentation Updates below) for the remaining SPA items (`phraseforge-spa-dialogs` etc.), since each will build a similar shell script that could hit the identical class of bug if it does any top-level `document.getElementById` lookup for an element that appears later in `layout.html`'s markup (the footer/status-bar, in particular).

**Second real regression found by the user, after `phraseforge-spa-dialogs` had already shipped**: the sidebar's `#language-filter` select (`layout.html`) navigates on change via a real page reload carrying `?language=...`, but `showList()` never read that query parameter — it only ever built its API query from `tagFilter`. The filter select itself appeared to work (its displayed value updates via an unrelated pre-existing localStorage-sync script), but the list never actually filtered. Fixed by reading `new URLSearchParams(window.location.search).get("language")` fresh on every `showList()` call (so it also survives in-page tag-filter navigation, which never changes the URL) and passing it through to `/api/v1/texts`. Verified against real data: a text in `deu` and one in `cmn` created, `/?language=deu` confirmed to call `/api/v1/texts?language=deu` and show only the German one. Recorded as a `[gotcha]` in `specs/memory.md` for every remaining SPA list view.

**Overall verdict**: clean, no regressions, every Acceptance Criterion validated end-to-end — including, uniquely for this feature, the actual client-side behavior itself, not just the server's half of it. Two real bugs reached the user before being caught (script-tag ordering, and the language filter never being read) — both root-caused precisely, fixed, and validated against real data; both lessons are now durable for the remaining SPA items.
