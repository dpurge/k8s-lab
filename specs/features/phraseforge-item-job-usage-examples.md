## Problem / Motivation

The roadmap item `phraseforge-two-step-vocabulary-generation` was split with the user into slices; this is the first: (1) usage phrase from generation plus examples in the item job (this spec); (2) the step-2 known-phrase check (`phraseforge-two-step-vocabulary-generation`); (3) the item job revising existing data (`phraseforge-item-job-revisions`); the prompts work is `phraseforge-usage-prompts`. Today step 1 (HandleGenerateVocab, prompt generate-vocabulary) emits `phrase {grammar} [transcription] = translation` per candidate, and the parser keeps only phrase, grammar and transcription: the model spends reply tokens on a Polish translation that is discarded. The item job (generate_vocabulary_item) sees only the phrase and the language names, so it has no context of how the word was used in the text and does not know the phrase's examples; and examples (spec phraseforge-item-examples) are only ever entered by hand. The user wants examples to accumulate as lists are generated, short (a noun phrase, verb with its object, or subject+verb), so that later slices can use them as context. Decisions taken with the user: the usage phrase is extracted by step 1 for every candidate (no extra call); it is a transient hint carried in the item job payload as `usage`, never stored on its own; the item job returns an optional `example` field, which the code stores through the examples store; names confirmed: payload field `usage`, reply field `example`, Go field `Usage string` on the candidate; vocabulary items only. Default prompts are not changed here: prompt-eval is the source of truth and the new prompts must be measured there (roadmap item `phraseforge-usage-prompts`); the code is backward compatible so it lands first, and a stored admin prompt row can be edited to try the new format on dev. For the later revisions slice the user also pointed out that a rewritten phrase can need a new transcription and new grammar tags (a phrase's identity is phrase, grammar and transcription together, so the stored ones go stale with the phrase); that slice must treat the three as one unit, which this slice does not do (it never changes a phrase).

## Acceptance Criteria

- [x] Step 1 line format accepts an optional usage: `phrase {grammar} [transcription] | usage` (the usage is the text after ` | `, a space, a pipe and a space, trimmed and NFC-normalised). A legacy `= translation` part is still accepted and ignored, before the usage if both are present (`phrase {g} [t] = translation | usage`), so admin prompt rows and Helm values that still ask for translations keep working. A usage over 80 characters (code points) is dropped and the candidate kept without one. The rejection reasons and the format help sent in correction rounds mention the usage part.
- [x] `generate.Candidate` (a vocabulary item plus `Usage string`) is what the vocabulary line parser returns and what the chunk loop de-duplicates by phrase, keeping the first occurrence's usage.
- [x] After the list sync, the item jobs queued by generation carry the `usage` of the candidate at the same position (empty when it had none); jobs from import, "Generate missing translations" and the per-item buttons carry none.
- [x] Item job payload is `{resource_type, item_id, locale, usage}` with `usage` optional (omitted when empty; vocabulary items only; an over-long usage is dropped, not an error).
- [x] `ItemSource` (store and ai) carries the phrase's current `Examples` (vocabulary only).
- [x] The vocabulary item prompt template has two new placeholders: `{{usage}}` (the usage text, or empty) and `{{examples}}` (the existing examples one per line, each prefixed `- `, or empty). A template without them behaves exactly as before; models item prompts are unchanged.
- [x] The vocabulary item reply schema has an optional `example` (string or null). Absent, null, blank or over 80 characters means no example and is not an error (no correction round, the job succeeds). A valid one is stored by `FillExample` (new store method): added to the phrase's examples only if fewer than 5 exist and it is not already there (exact, after NFC), under the same item-gone and phrase-changed guards as the other item writes (ErrItemGone/ErrItemChanged skip the job). The job result's `applied` map gains `example`.
- [x] Default prompts, config.yaml, Helm values and prompt-eval are not changed; with the current prompts behaviour is unchanged (no usage in replies, no `example`).
- [x] Tests: parser (usage only, legacy translation only, both, over-long usage dropped, diacritized Arabic and CJK bytes kept, malformed lines still rejected with a reason), generation flow (usage reaches each item job's payload by position; no usage when the candidate had none), store (ItemSource examples; FillExample adds, respects the cap of 5 and duplicates, gone/changed), prompt rendering of the two placeholders, item job with a fake store and a fake Ollama (example stored; blank, null, over-long ignored; a template without the placeholders unchanged). Verified on the dev k3d cluster with at most one real model call: a dev-only admin prompt row (reverted afterwards) that asks for `example`, one item job with a usage, and the example stored.

## Approach

(1) Parser: `Candidate`, the optional `| usage` and legacy `= translation` handling, rejection reasons and format help, parser tests.
(2) Generation flow: `generateItems` over candidates; `syncVocabItems` hands the usage of each stored item (same position as its candidate) to `enqueueItemBackfill`, then `ItemJobsFor`/`NewItemJob`, which put it in the payload; tests of the planning.
(3) Store: `ItemSource.Examples` and `FillExample` in internal/vocabulary/itemjob.go, tests.
(4) Item job: payload `usage`, `ai.ItemSource.Examples`, `ItemStore.FillExample` (main.go adapter), the two placeholders, the optional `example` in the schema and response parsing, the write after the other writes, tests with a fake store and fake Ollama.
(5) Deploy to dev (task deploy-phraseforge) and verify with at most one real model call using a dev-only admin prompt row, restored afterwards; the dev queue is checked first for pending model jobs.
(6) Documentation (README placeholders, CHANGELOG), spec, memory if anything durable.

Key decisions: the usage is a transient payload hint, not a column (nothing to migrate, nothing stale); the code, not the model, enforces the example limits at the store; parse and prompts are backward compatible so the code can ship before the prompts; the optional example is ignored rather than corrected when invalid, to avoid an extra model call. Alternatives considered: storing the usage directly as the example in the sync, with no extra reply tokens in the item job (cheaper, deterministic; not chosen because the user chose the item job returning `example`; worth revisiting after the prompts are measured); having step 2 extract usage for every candidate (an extra long call per chunk, about +5 minutes per list); passing the whole text chunk to every item job (about +2000 prompt tokens per job). Costs once the prompts use the new fields (estimates from 5166 measured calls: 37 s and 889 prompt tokens and 49 reply tokens per item job, about 250 ms per reply token): step 1 about +10-15 reply tokens per candidate (about +3 s each), offset if the prompt drops the discarded `= translation` (a prompt change, not here); item job about +100 prompt tokens and +15-25 reply tokens, about +4-6 s per job (+10-17%). Risks: a phrase containing ` | ` is mis-split (rare; the correction rounds apply); known phrases still get no jobs, so they gain no example until slice 2; nothing changes until the prompts change; the later revisions slice must rewrite phrase, transcription and grammar together (see Problem / Motivation).

## Affected Areas

phraseforge/internal/generate/parse.go and generate.go (parser, Candidate, syncVocabItems, enqueueItemBackfill) and tests; phraseforge/internal/generate/correct.go (generic chunk loop over candidates, format help); phraseforge/internal/ai/itemjob.go, itemcalls.go, itemprompt.go, itemresponse.go, ai.go (payload, ItemSource, ItemStore, placeholders, schema, example write) and tests; phraseforge/main.go (the ItemStore adapter); phraseforge/internal/vocabulary/itemjob.go (ItemSource.Examples, FillExample) and tests; callers of ItemJobsFor in phraseforge/internal/server (pass no usage); phraseforge/README.md (prompt placeholders); phraseforge/CHANGELOG.md.

## Out of Scope

The step-2 known-phrase check and any change to which phrases get item jobs (`phraseforge-two-step-vocabulary-generation`); the item job revising existing data: appending senses to translations, and rewriting a phrase together with its transcription and grammar tags (`phraseforge-item-job-revisions`); authoring or changing default prompts, config.yaml, Helm values or prompt-eval (`phraseforge-usage-prompts`); models items; storing the usage anywhere; per-locale examples.

## Implementation Notes

1. Step 1, parser: `generate.Candidate` (embeds the vocabulary item, adds `Usage string`); `splitUsage` splits at the first whitespace-pipe-(whitespace or end) with the regexp `\s\|(?:\s+|$)`, so a pipe inside a word is not a separator and later pipes belong to the usage; what precedes it is parsed as before, a legacy `= translation` included and ignored; the usage is trimmed and NFC-normalised and dropped when over 80 characters; a line starting with `|` is rejected with its own reason; the correction-round format text shows `| usage` as one more optional part next to `= translation` so it stays valid for old and new prompts. The chunk checkpoints store the parsed items as JSON, and a checkpoint saved by older code (plain items, flattened into each entry) still decodes into candidates with no usage (tested). With this module's Go language version a composite literal cannot name the promoted fields of an embedded struct, so literals are written `Candidate{Item: vocabulary.Item{...}}`.
2. Step 2, generation flow: payload field `usage` (omitted when empty); `NewItemJob` and `ItemJobsFor` take a `usage` argument and put it in every job of the item; it is carried for vocabulary items only, trimmed, NFC-normalised, and dropped when over `ai.MaxUsageChars` (80; a test keeps it equal to `vocabulary.MaxExampleChars`, since `ai` does not import the store); `syncVocabItems` pairs each stored item with the candidate at the same position (`usagesByPosition`) and logs and passes no usage when the counts differ; import, "Generate missing translations", the per-item buttons and models generation pass none.
3. Step 3, store: `ItemSource.Examples` and `Store.FillExample` in internal/vocabulary/itemjob.go: the phrase row is locked, the example is added last when fewer than 5 exist and it is not already there (after NFC), a blank example is not applied, one over 80 characters is `ErrInvalidExamples`, a deleted item is `ErrItemNotFound` and a changed phrase `ErrItemChanged`.
4. Step 4, item job: placeholders `{{usage}}` and `{{examples}}` (`formatExamples`: one per line, each prefixed `- `) in `ItemPromptVars`/`renderItemPrompt`; `ai.PromptPlaceholders` lists them for `vocabulary_item` only (so the admin form shows them; this was not in the acceptance criteria); optional `example` in `VocabularyItemSchema`; the reply field is decoded leniently, anything that is not a string means no example, so a wrong-typed value costs no correction round (the criteria named blank, null and over-long; wrong types are the same case); `usableExample`; `applied` gains `example`; `ItemSource.Examples`, `ItemStore.FillExample` and the main.go adapter.
5. Deviations from the Approach: none. Default prompts, config.yaml, the Helm values and prompt-eval were not changed, as specified.

## Validation

- Baseline before the slice: build and the full suite green with PHRASEFORGE_TEST_DSN and PHRASEFORGE_TEST_DB set to the dev Postgres (port-forward): 326 passed, 1 skipped at the end of the examples feature.
- After: `gofmt -l .` clean; `go build ./...` and `go vet ./...` clean; `go test -count=1 -v ./...` with both variables set: 358 PASS (32 new), 0 FAIL, 1 SKIP (TestAdminConfigExportImportRoundTripDB, which wipes the database and needs PHRASEFORGE_TEST_DB_REPLACE_ALL=1; deliberately not run). Frontend: `npm test` in internal/server/static/components, 45 passed. No regressions.
- New tests: parser (14 usage cases incl. diacritized Arabic and CJK bytes, the limit at 80, a leading pipe, an old checkpoint decoding); payload and builder; pairing of candidates with stored items; a real-database test that runs `syncVocabItems` and reads the queued jobs' payloads back (each item's two jobs carry exactly its own usage, none for a candidate without one); store `ItemSource`/`FillExample` including a concurrency test (two jobs, room for one: exactly one applied; run 25 times and once under the race detector); prompt rendering of the placeholders (a template without them renders exactly as before); reply parsing and decision of `example`; the write path; an end-to-end `HandleItemTranslation` test with a real database and a fake Ollama (the model receives the usage and the known examples, the returned example is stored; an older template is sent unchanged; a blank, null, wrong-typed or over-long example succeeds on the first call with nothing stored and no correction round; an item gone at the example write skips the job).
- Mutation checks, all caught and restored: breaking the usage pairing (unit and real-database tests failed); removing the placeholder substitution (end-to-end and rendering tests failed); making a wrong-typed example a hard error (end-to-end test failed after three attempts, parser test failed).
- Dev k3d cluster: deployed with `task deploy-phraseforge` (no migration in this slice); queue checked empty first. One real model call (gemma4:12b via the dev Ollama), first attempt, no correction round: a dev-only admin prompt row (the default item prompt plus an `example` field, rule, `{{examples}}` and `{{usage}}` blocks and examples in the two samples) and one item job for 拥有 (2 seeded examples, existing Polish translation, a synthetic usage `拥有极高的知名度`) finished `done`, 30.5 s, 825 prompt tokens, 66 reply tokens (baseline 37 s, 889 and 49: about +17 reply tokens, within the +15-25 estimate), and stored the model's example as a third one; the model copied the usage verbatim, and its translation (`posiadać; mieć`) differed from the stored one and was correctly not written (translations are only filled when blank). Reverted afterwards: prompt row, test job and added example deleted; queue empty.
- Not covered: prompt quality across languages and scripts (roadmap item `phraseforge-usage-prompts`); a real list generation with a prompt that asks for `| usage` (no default prompt does yet); known phrases still get no jobs; production unaffected (no migration); validate-specs could not be run (script missing).
