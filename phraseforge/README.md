# phraseforge — language-learning app

> Part of the [k8s-lab](../README.md) cluster. See the root README for cluster setup, `task`
> usage, image builds, and shared infrastructure (Postgres, Qdrant, Adminer).

A Readeck-inspired Go app for language-learning content: login, per-language teacher/student roles, and four resource types —

- **Texts** — markdown articles, with an optional transcription and a translation (in the reader's own site language). Create via form, paste text, upload a file, or ingest from a URL; title and content are cleaned automatically in the background.
- **Dialogs** — the same, using phraseforge's own turn-based markdown syntax (`--:`/`@Name:` turns). Same creation methods as Texts, with background processing for title and content cleanup.
- **Vocabulary** and **Models** — structured lists (not markdown): edited one item at a time, with proper IME support on non-Latin scripts. A vocabulary item is phrase/grammar/transcription (common) plus up to 5 short usage examples (source-language text, shared like the translations and shown below the notes) and translation/notes (per site locale, en/pl); a model item is the same minus grammar/notes — cli-tools' own `{start-models}` block, described as "vocabulary without a grammar tag or notes". Each distinct phrase (language, script, phrase, grammar, transcription) is stored once and linked from every list that has it, so its translations are shared, an already-translated phrase is not translated again, and editing it changes it in every list that uses it. Phrase text is trimmed and Unicode-normalised (NFC) before it is stored or compared. In an export every item has an `id`; importing a file you edited outside the app updates the items it names by `id` (phrase, grammar, transcription, translations and examples: an `examples` key replaces the phrase's examples, an empty list clears them, a missing key leaves them), a line without an `id` is a new item, and items missing from the file are removed from the list.
- **LLM assist** — edit pages can generate transcription and translation with Ollama or OpenRouter-compatible chat APIs. Admins can set system prompts per request kind, source language, and target language.

Shares the `data` namespace's Postgres server with `dictionary`, but its own database (`phraseforge`) and its own migration path — the two apps' schemas never mix. Shared Postgres/LLM helper code lives in `../shared`.

## Deploy and migrate

```sh
task start-k8s              # cluster must be running first
task deploy-postgres          # Postgres + Adminer (see root README)
task deploy-phraseforge        # build the image, check its size, migrate, apply phraseforge/k8s/, wait for Ready
```

`task deploy-phraseforge` builds and size-checks the image, runs the database migration Job
(creates the `phraseforge` database if missing and applies `internal/db/schema.sql`, which
is idempotent), then applies `phraseforge/k8s/deployment.yaml` (Deployment/Service/Ingress). Run
`task migrate-phraseforge-db` on its own later to re-apply the schema after a change without a
full redeploy. `task delete-phraseforge` removes the Deployment/Service/Ingress only — it leaves
the migration Job and the database alone.

## LLM configuration

LLM configuration is file-based with per-purpose (transcription/translation) defaults, and per-kind admin overrides of provider, model, think and timeout:

**Configuration file:** mounted at `CONFIG_FILE` (default `/etc/phraseforge/config.yaml`), containing:
- `providers.ollama.baseURL` and `providers.openrouter.baseURL` — provider connection URLs.
- `providers.ollama.firstTokenTimeoutSeconds` (default 300) and `providers.ollama.idleTimeoutSeconds` (default 60) — Ollama calls stream, and fail if no output arrives within the first limit (model load + prompt processing) or if output then stops for longer than the idle limit. They belong to the provider because they reflect how fast that host runs a model.
- `<purpose>.timeoutSeconds` (default 1800) — overall cap on one call, a backstop against runaway output; the streaming limits above are what catch a hung call. An admin LLM rule's own timeout overrides it.
- `<purpose>.maxAttempts` (default 3) — total attempts for one LLM call, shared between replies that fail validation (the rejected reply and the exact error are sent back to the model) and transient failures (HTTP 5xx, connection errors, a stream that ends early, idle stalls), which wait 5s and then 15s before retrying. First-token and overall timeouts are not retried. Zero or less means 3.
- `ingest.maxContentBytes` (default 24576) — largest raw content, in bytes, that one ingest request may carry. Content is processed in chunks sized from each purpose's `numCtx`, one LLM call per chunk, so a larger limit means a longer-running job; the queue runs one job at a time.
- `vocabularyItem.{provider, model, think, timeoutSeconds, prompt}` and `modelsItem.{...}` — one structured (JSON) call per vocabulary/models item per site locale. `prompt` is a template with the placeholders `{{sourceLanguage}}`, `{{targetLanguage}}`, `{{phrase}}`, `{{grammarPrompt}}`, `{{transcriptionPrompt}}` (the same names as the prompt-eval setup, so a tuned template can be pasted in unchanged; the last two are the language's snippets, see below). A vocabulary item prompt may also use `{{usage}}` (how the word was used in the generated text, from an optional ` | usage` part at the end of a generate vocabulary line; empty for items not made by generating a list) and `{{examples}}` (the phrase's examples so far, one per line, each prefixed `- `; empty when there are none); a template without them renders exactly as before. The reply is constrained by a JSON schema and validated before any field is stored, and only blank fields are written; a vocabulary reply may also carry an optional `example` (a short phrase of at most 80 characters), which is added to the phrase's examples when there are fewer than 5 and it is new, and is ignored, without a correction call, when it is blank, not a string or too long. A vocabulary reply may also carry an optional `rewrite` (`{"phrase", "grammar", "transcription"}` or null) for a phrase that is not in dictionary form (a different case, a joined form): it is applied only when the job carries a usage (generated from a text) and the new phrase differs from the stored one after trim and NFC, as one change like a manual edit of the phrase (the item keeps its id, every list that links the phrase shows the new values, translations, notes and examples stay with it, and a phrase that already exists with exactly those values is merged into). An empty grammar or transcription keeps the stored one, and a language without that section ignores it. The rewrite is applied after the job's other writes; if it is skipped or fails it is logged and the job still succeeds. A `rewrite` that is not that object is ignored without a correction call. Translations of other locales are not redone when a phrase is rewritten. A vocabulary item prompt may also use `{{translation}}` (the phrase's existing translation in the job's locale, empty when there is none), and the reply may carry an optional `newSense` (one extra meaning in the target language, or null). A new sense is appended to the locale's existing translation as `old; sense` (the old text kept as the prefix) only by a job made for a phrase the check marked `needsSense` (the job's payload has `sense`), and only if the translation is not blank and the sense is not already one of its senses (compared ignoring case, trim and Unicode form); notes are untouched and there is no cap on the number of senses. Models often put the extra meaning into `translation` instead of `newSense`, so when `newSense` is empty the senses of the reply's `translation` that the existing one lacks are used, but only if the reply keeps every existing sense. A skipped or failed append is logged and the job still succeeds.
- `checkVocabulary.{provider, model, numCtx, think, timeoutSeconds, maxAttempts, prompt}` — the check of known phrases after a vocabulary list is generated. Phrases that already have a translation or an example and came with a usage (` | usage`) are sent, numbered with their usage, examples and translations, in one call per list (20 phrases per call at most); the model replies `{"results":[{"n":1,"needsExample":true,"needsSense":false}]}` for each (`needsSense` means the usage shows a meaning that none of the existing translations covers; an absent or non-boolean `needsSense` counts as false). A phrase marked `needsExample` gets one item job, for the first site locale, which may return an `example` for it; a phrase marked `needsSense` gets one item job for every site locale in which it already has a translation, each of which may append a new sense there (see the item reply above); new phrases and phrases without a usage are not sent and are queued as always. A reply that is not that JSON is sent back for correction within `maxAttempts`; if the call still fails, it is logged with the list id and skipped, and the generate job succeeds. `prompt` is a template with `{{sourceLanguage}}` and `{{candidates}}`. In Admin > LLM it is the kind "Check vocabulary" (`check_vocabulary`).
- `reviewVocabulary.{provider, model, numCtx, think, timeoutSeconds, maxAttempts, prompt}` — the review of one vocabulary item (job kind `review_vocabulary_item`, one structured call per item). It has its own `provider` and `model`, like every purpose; to review with a more capable model set both here (for example `provider: openrouter` and a model) or in an Admin > LLM row for the kind; no other purpose changes. The prompt's placeholders are `{{sourceLanguage}}`, `{{phrase}}`, `{{grammar}}`, `{{transcription}}`, `{{examples}}` (numbered), `{{translations}}` (one line per locale, English first as the reference, notes below), `{{dictionaryPrompt}}`, `{{grammarPrompt}}`, `{{transcriptionPrompt}}`. The reply is a schema-constrained set of `{ok, suggestion, reason}` checks for phrase, grammar and transcription, per-locale translations and notes, and per-example keep/remove/shorten. Nothing is written by the job: its proposals are stored per item (table `vocabulary_reviews`, one review per item, replaced by the next one) and shown in the Review dialog of the vocabulary page, where an editor applies or dismisses each (or all). A phrase proposal carries its grammar and transcription and is applied as one change; a proposal is only applied while the item still has the reviewed phrase and the value it was about (otherwise it is a conflict and stays open). Checks for a field whose language has no matching snippet (dictionary form, grammar, transcription) are ignored. API (edit right on the list's language): `POST /api/v1/vocabulary/{id}/review` and `POST .../items/{position}/review` queue jobs (never a second one for an item that has one waiting), `GET .../reviews`, `GET .../items/{position}/review`, `POST .../review/apply` and `.../review/dismiss` with `{"indexes": [...]}` (none = every open proposal).
- `reviewModels.{provider, model, numCtx, think, timeoutSeconds, maxAttempts, prompt}` — the review of one models item (job kind `review_models_item`, one structured call per item). It has its own `provider` and `model`. The prompt's placeholders are `{{sourceLanguage}}`, `{{phrase}}`, `{{transcription}}`, `{{translations}}` (one line per locale, English first as the reference) and `{{transcriptionPrompt}}`. The reply is a schema-constrained set of `{ok, suggestion, reason}` checks for the phrase, the transcription and each locale's translation. Nothing is written by the job: its proposals are stored per item (table `models_reviews`, one review per item, replaced by the next one) and shown in the Review dialog of the models page, where an editor applies or dismisses each (or all). A phrase proposal carries its transcription and is applied as one change; the transcription check is ignored for a language without a transcription snippet; a proposal is only applied while the item still has the reviewed phrase and the value it was about (otherwise it is a conflict and stays open). The models page also has a Generate button that queues the translations and transcriptions the list still lacks, like the vocabulary page's. API (edit right on the list's language): `POST /api/v1/models/{id}/generate-missing-translations`, `POST /api/v1/models/{id}/review` and `POST .../items/{position}/review` queue jobs (never a second one for an item that has one waiting), `GET .../reviews`, `GET .../items/{position}/review`, `POST .../review/apply` and `.../review/dismiss` with `{"indexes": [...]}` (none = every open proposal).
- `reviewTranscription.{provider, model, numCtx, think, timeoutSeconds, maxAttempts, prompt}` and `reviewTranslation.{...}` — the reviews of a text's or dialog's transcription and of its translations, each with its own model, numCtx and prompt (`provider` and `model` are set on each purpose; none falls back to another's). The transcription and the translations are reviewed separately: the text and dialog view pages have a Review transcription and a Review translation button (editors only) and a status line with a link per part that opens the proposals dialog. One job (kind `review_text`, payload `{resource_type, resource_id, part}`) and one structured call per part, which sees the source text, the part under review and the vocabulary list generated from the text (up to 100 phrases with their translations; English translation first as the reference); a text whose source and reviewed part exceed 12000 characters is split into paragraph chunks (blank-line separated) of at most 12000 characters, one call each, and the chunk results are merged into one proposal per field; this needs the source and the reviewed part (each locale, for translations) to have the same number of paragraphs, and a paragraph pair over the limit cannot be split, otherwise the job fails with a message naming the counts. The transcription is only reviewed when the text has one and its language has a transcription snippet. A proposal is the whole corrected transcription or translation of one locale; nothing is written by the job. Proposals are stored per resource and part (table `resource_reviews`, replaced by the next review) and applied or dismissed one by one or all open; a proposal is refused while the source text changed since the review (409, the review is shown as outdated) and is a conflict, left open, when the transcription or translation was edited since. API (edit right on the language): `POST /api/v1/{texts|dialogs}/{id}/review/{transcription|translation}` queues (never a second job for a part that has one waiting), `GET` the same path returns `{pending, review}`, and `POST .../apply` and `.../dismiss` take `{"indexes": [...]}` (none = every open proposal).
- **Choosing a bigger review model:** all four review purposes (`reviewVocabulary`, `reviewModels`, `reviewTranscription`, `reviewTranslation`) run on gemma4:12b unless set. To use a bigger one, set `provider` and `model` of the purpose in config.yaml (in the cluster: `phraseforge.<purpose>` in jdp-helm `jdp-frontend/values.yaml`), or per language in Admin > LLM (kind `review_vocabulary`, `review_models`, `review_transcription` or `review_translation`) without a redeploy. With the `ollama` provider the model must be pulled on the server (jdp-helm `jdp-backend/values.yaml` `ollama.models`) and fit its memory and storage. Every purpose names its own `provider` and `model` (a config file that leaves one blank fails at startup, naming the purpose); to review everything with a bigger model change all four.
- **Pages that wait for background work** (the review columns of the vocabulary and models pages, the review line of a text or dialog, and the Jobs list) refresh themselves through one helper, `static/js/poll.js`: only while something is pending or running, after 8 s, then 15 s, then 30 s between requests; not while the browser tab is hidden (one refresh when it is visible again); not for more than 15 minutes (any click starts it again); and not after leaving the page. Its timing is covered by `static/components/poll.test.js` (`npm test` there).
- `transcription.{provider, model, think}` and `translation.{provider, model, think}` — per-purpose defaults (provider is `"ollama"` or `"openrouter"`; model examples: `"gemma4:12b"` for Ollama, `"meta-llama/llama-2-70b"` for OpenRouter; think is boolean, default false).

**Credentials:** API keys come from environment variables only, never from the config file:
- `OLLAMA_API_KEY` — Ollama API key (empty for local Ollama, which needs no auth).
- `OPENROUTER_API_KEY` — OpenRouter API key.

**Admin overrides:** in the admin panel's LLM tab, admins can set provider, model, and think (enable/disable thinking) (and timeout) per kind, overriding the purpose defaults for that specific (kind, source_language, target_language) combination. A newly saved row inherits the purpose default. The prompt text is never stored per row: it is the purpose default, shown read-only in the LLM tab, and a language's rules come from Admin > Languages.

**Default prompts:** every purpose's default prompt is a file of prompt-eval's `prompt/phraseforge/default/system/` (`generate-title.txt`, `generate-vocabulary.txt`, ...), embedded in the binary from `internal/config/prompts/default/`. prompt-eval is the source of truth: `npm run sync-prompts` there copies the files into this repository and `npm run check-sync` fails when the copy differs. A prompt in `config.yaml` replaces the embedded default for its purpose, and an admin row replaces both. In Admin > LLM a new prompt starts from the default for its kind, with its placeholders visible, and the form lists the placeholders available for that kind. The admin kind names match the file names ("Generate title" is `generate-title.txt`).

**Language snippets:** Admin > Languages holds, per language, a grammar-tag snippet, a transcription snippet and a dictionary-form snippet, one tile each. A snippet is defined once and inserted wherever a prompt contains its placeholder: `{{grammarPrompt}}` (grammar-tag conventions) `{{transcriptionPrompt}}` (transcription system) and `{{dictionaryPrompt}}` (the dictionary form of the phrases, used by the review prompt and any prompt that contains it) in the vocabulary/models item prompts and in the generate transcription, generate vocabulary and generate models prompts. A language without a snippet gets nothing, except that a language whose IME config needs transcription gets "Transcribe using the standard romanization for this language.". Grammar and transcription are only generated for an item whose language has the matching snippet. A prompt in `config.yaml` only uses a snippet if it contains the placeholder. Snippets are part of the admin configuration export/import.

**Example config.yaml:**
```yaml
providers:
  ollama:
    baseURL: http://host.docker.internal:11434
    firstTokenTimeoutSeconds: 300
    idleTimeoutSeconds: 60
  openrouter:
    baseURL: https://openrouter.ai/api/v1
transcription:
  provider: ollama
  model: gemma4:12b
  think: false
  timeoutSeconds: 1800
translation:
  provider: ollama
  model: gemma4:12b
  think: false
  timeoutSeconds: 1800
```

## Tests

`go test ./...` runs everything except the database tests of `internal/vocabulary`, `internal/models` and the vocabulary and models API tests of `internal/server`, which are skipped unless `PHRASEFORGE_TEST_DSN` is set to a Postgres URL (`internal/jobs` and the admin config round trip use `PHRASEFORGE_TEST_DB` instead). Each of those tests applies `internal/db/schema.sql` into its own throwaway schema and drops it afterwards, so a development database is safe to point at.
